# 我们研究过哪些衣橱 App？为什么都没用？我们的理念差在哪

> 整理自 2026-09-20 的竞品调研（第一~四轮）＋后续 20 天的实践验证。
> 用途：① 回答「为什么不直接用现成的」② 可做成一期视频/一篇分享 ③ 给分享源码的人讲清定位。

---

## 一、一句话结论

★ **市面上的衣橱 App 都是「推荐系统」——告诉你今天穿什么；我要的是「组合优化器」——算你最少用几件衣服能搭出最多的效果。**

这不是同一个问题的两种做法，★ **这是两个不同的问题。**

---

## 二、我们到底研究过哪些？

分四类。

### 第一类：国内的重合产品 —— 「搭搭」

**它是谁**：创业公司做的，2022 年上线，约 200 万用户（号称一年从 0 到 100 万），总投资约 1000 万人民币，几乎全砸在研发上。至今仍在更新。

**为什么它是重点研究对象**：★ **它的功能几乎覆盖了用户最初的全部构想**——批量上传、自动抠图识别品类颜色材质、AI 搭配、天气推今日穿搭、通勤/旅行/约会提前排、穿搭日记、穿着次数与成本、**种草衣橱（买前辅助决策）**、闲置/丢弃状态、存放位置、衣橱统计、家庭共用。

换句话说：★ **我一开始想要的，它都有。**

**它的弱点**（来自老用户评价和第三方评测）：页面杂乱、「打开像进逛街页面」；2024 年起收费且没买断被骂；★ **AI 搭配「推来推去就那几套」**，衣服少于 20 件时更没灵感；算法精度和社区粘性都不够厚。

**同质化的一片**：WearWow、Mué、今穿、简衣穿搭、TrendSeek、浪漫衣橱、AI衣橱管理……★ **绝大多数是低质套壳或下载站应用。**

### 第二类：国外的成熟产品

| 名字 | 什么来头 | 被指出什么问题 |
|---|---|---|
| **Whering** | 英国，下载量很大 | 推荐**模板化/随机** |
| **Acloset** | 韩国，Google Play 系（跟搭搭同源） | ★ **反复推同样那 5 件** |
| **Cladwell** | 美国，主打极简胶囊衣橱 | ★ **太安全**——永远给你配中性色，无聊 |
| **Indyx** | 美国 | 被评 **play safe（不敢冒险）** |
| **Elara / Demna / Alta** | 各类新秀 | 买前预判**只停在定性描述**；Alta 靠返佣赚钱 |

### 第三类：开源方案 —— Wardrowbe（差一点就用它了）

**它是谁**：GitHub 上的开源项目（MIT 许可），约 270 次提交，**在我们调研时两天前刚提交过，高度活跃**。自托管，Docker 跑 4 个容器（FastAPI + Next.js + React Native + PostgreSQL），约 4GB 内存，树莓派 5 / NAS / VPS 都能跑。带 iOS + Android 原生 App，能直接拍照入库。

**它的 AI**：视觉模型自动识别品类/颜色/图案/风格/正式度，★ **不需要手动打标签**，支持 OpenAI / Ollama / 本地模型，可以选本地跑让照片不出内网。

**它的功能**：天气+场合推荐、单品搭配查询、穿着记录与评分学习、衣橱分析、洗衣提醒、虚拟试穿、家庭共用、定时推送、★ **8 种语言含简体中文**。

**缺口**：单次穿着成本（CPW）官方标注"计划中"没做；旅游打包清单没提；★ **没有替换率的量化**。

**另一个**：OpenWardrobe（Flutter + Supabase）2025 年 2 月后停更、没有 AI，★ **直接排除。**

### 第四类：不是 App，但被拿来研究过的

- **小红书的穿搭 AI** —— 被明确列为「要区别于」的对象（原因见下）
- **一篇小红书笔记《26 度穿衣法则》** —— ★ **这个反而被采纳了**，成了整个引擎的核心公式

## 三、为什么最终一个都没用？

### 原因一：★ 录入成本是死亡线，谁都没解决

这是赛道公认的第一条死因：

- ★ **大多数衣橱 App 用户录不到 30 件就放弃了**
- 平均一个人的衣橱有 100–150 件，按每件 2–3 分钟算，★ **要 4 到 8 小时**
- 有数据说约 **50% 的时尚类 App 用户 30 天内就流失了**

★ **「搭搭」功能全都有，但它照样死在这一关上。** 功能齐全 ≠ 有人用得下去。

### 原因二：★ 「照片墙 ≠ 风格模型」

大多数产品停在"目录"层面——它知道你有件白衬衫，但它**不理解这件衬衫是什么版型、什么正式度、什么材质**。

结果推荐就走向两个极端：

- 要么**安全但无聊**（Cladwell 永远配中性色、Indyx 不敢冒险）
- 要么**随机**（Whering 被指模板化、Acloset 反复推那 5 件）

★ **用户的原话是「推来推去就那几套」——这不是幻觉，是结构性的。**

### 原因三：★ 目标函数根本不一样（最关键的一条）

这一条是整个决策的转折点。用户当时反驳的原文：

> 「他们的设计目标和我的都不一样，我主要是为了能够让我的衣服真的变成衣橱，最少的衣服搭配出最多的效果，而且我也不为盈利，只想做一个自己能用的。」

**拆开看，两个目标的差别是：**

| | 商业 App 优化的是 | 我优化的是 |
|---|---|---|
| 目标 | 今日决策满意度 + **使用时长/活跃度** | **组合空间效率** |
| 想让你 | 多打开、多买衣服 | **少买衣服** |

★ **商业动机是天然相反的。**

- **Alta** 是返佣模式（affiliate-funded）——★ **靠你买衣服赚佣金**
- **搭搭** 有完整的「种草—拔草闭环」（官方称转化率 8%）＋社区＋商城导流

★ 所以有一句很重的话：**一个以「让你少买衣服」为目标的 App，在商业上没有动机被做出来。** 这不是能力问题，是★ **利益冲突**。

而这恰恰是"我自用、不为盈利"带来的★ **结构性优势**——我可以做那个商业上不该存在的东西。

### 原因四：Wardrowbe 看着能直接用，为什么也没用？

第一轮我确实推荐过「自托管 Wardrowbe」或「fork 它」。但第三轮自己推翻了：

★ **它覆盖的 80% 里，有一半我根本不需要**（家庭共享、社区、虚拟试穿、定时推送、8 种语言），而我真正要的 100%，★ **全都在"没人做的那 20%"里。**

**所以 Wardrowbe 对我的实际价值从 80% 降到约 30%，fork 的性价比直接反转。**

最后选的折中方案是：**自己写 + 只在录入时一次性调用视觉 API 批量打标**，之后所有分析都在本地算，永久离线、零服务器、零运维。

## 四、我们的理念，跟他们差在哪

**四句话：**

1. ★ **他们问「今天穿什么」，我们问「这件值不值得留 / 买」。**
   他们的核心动作是"给我一套"；我们的核心动作是"算 ΔN"。

2. ★ **他们的收入来自你买衣服，我们只关心你的组合空间够不够高效。**
   我们有一个铁律：★ **所有搭配 100% 由你已有的衣服组成，绝不输出"建议你买一件 XX"。** 这是区别于小红书穿搭 AI 的根本。

3. ★ **他们停在「照片墙」，我们建了「衣橱图」。**
   把每件衣服当**节点**，把"能不能搭"当**边**，衣橱就变成一张分层图；一套搭配 = 一条合法路径。这样才能算出一个**硬数字**。

4. ★ **他们只会定性说"能搭几件"，我们给硬数字：ΔN、替代率 X%、该淘汰哪件。**

**一句话总结差异**：

| | 市面上的 App | 胶囊衣橱 |
|---|---|---|
| 类型 | 推荐系统 | **组合优化器** |
| 核心问题 | 今天穿什么 | **这 30 件，买哪件最值、扔哪件最亏** |
| 输出 | 几套搭配 | **一套搭配 + 一堆硬数字** |
| 收入动机 | 让你多买 | ★ **让你少买** |
| 数据深度 | 目录层（照片墙） | **图模型（衣橱图）** |

## 五、★ 全市场的空白 —— 我们做的那「没人做的 20%」

这是整个项目立得住的地方，四条：

**1. 量化替换率 + 进一件出一件。**
所有"买前预判"都停在**定性描述**层——搭搭的种草衣橱、Elara 的 gap analysis、Demna 的 pre-purchase 问题清单，★ **没有任何产品给出硬数字**：新增几套组合、替代率百分之多少、该淘汰哪一件。

ⓘ 而且这事有个耐人寻味的地方：★ **因为商业产品的收入来自让你买衣服，没有人有动机做这个功能。**

**2. 旅游场景没人用「集合覆盖/复用率」算法。**
大家都是在**生成打包清单**（"建议带这些"），★ **没人把它当成一个集合覆盖问题去求解**——最少件数覆盖最多场景。

**3. 没人解释「这套为什么好」。**
搭配质量的评价标准不透明，给推荐但不说理由。

**4. 数据导出普遍缺失。**
换个 App 就得重拍一遍。★ 我们的 `data/` 就是普通文件，随时能拷走。

## 六、⭐ 一个重要的修正：我们并不是全都不要

★ **有两样东西，我们反而是从竞品/公开资料里学来的**——这点要讲清楚，不然显得像为了不同而不同：

1. **「26 度穿衣法则」** —— 用户甩来的那篇小红书笔记，后来成了整个温度引擎的核心公式（而且是人民日报、科普中国、央广网多源一致的老规则）。
2. **「录入成本是生死线」这条判断** —— 是从全赛道的数据（录不到 30 件就放弃、4–8 小时、50% 流失率）里读出来的，★ **它直接决定了产品最优先要解决的是什么。**

★ **我们否掉的不是"功能"，是"目标"。** 功能可以学，目标必须自己定。
