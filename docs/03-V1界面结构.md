# V1 界面结构

技术形态：**移动端优先的网页（PWA）**。后端 FastAPI + SQLite，前端 HTML/JS，跑在你那台 Windows 电脑上，手机连同一 WiFi 访问。

首页 = 今天穿什么（引擎的输出）。衣橱图 = 体检报告（引擎的输入可视化）。**互不冲突，前者主、后者副。**

---

## 屏 0 · 录入工作台（电脑端为主）

**这是最重要的一屏，也是唯一建议在电脑上做的事。**

> **实现后修正（2026-09-20）：原来的「一列表单 + 逐件确认」是错的。**
> 用户第一轮试用就指出「太复杂了」。表单把 10 个字段平铺在每件衣服上，20 件就是 200 个
> 待填项 —— 而这正是「录到第 20 件就放弃」的直接原因。
> 改成**卡片网格 + 槽位一键切换**：每件只点一下槽位，其余全部自动填。
> 配了视觉模型则连这一下也省掉。下面的线框已按实现更新。

```
┌──────────────────────────────────────────────────┐
│  录入工作台                        待入库 18 件    │
├──────────────────────────────────────────────────┤
│  点这里选照片（可多选）                            │
│  ┌────────┬────────┬────────┐                    │
│  │ 图  ✓92%│ 图  ✓88%│ 图  待选│  ← 卡片网格       │
│  │ ●藏蓝  │ ●卡其  │ ●深灰  │                    │
│  │[内][中][外]…      │                            │
│  │[下][鞋][饰]       │                            │
│  │[针织开衫 ▾]       │                            │
│  │正式3·厚2·5~18℃    │                            │
│  └────────┴────────┴────────┘                    │
│                                                  │
│  [ ↻ 全部识别 ]  [ 全部设为… ▾ ]                  │
│                                                  │
│              [ 全部入库（18 件）]                 │
└──────────────────────────────────────────────────┘
```

**设计要点**

- **槽位是唯一的必填项，一次点击。** 六个按钮（内搭/中层/外层/下装/鞋/配饰）就地点，
  不再用下拉——下拉在桌面端是两次交互，按钮是一次。
- **其余 10 个字段全部按品类自动填**（`app/catalog.py` 的 34 个品类默认值表）。
- **颜色本地测，不填不选。** 卡片上直接显示色块和色名，只在测错时才手动改。
- **未处理的卡片带橙色左边框**，扫一眼就知道还剩哪几张。
- **一次上传、一次批量入库**，不做逐件确认。批量接口 `POST /api/items/bulk`
  逐条插入、单条失败不影响其余。
- 配了视觉模型（右上角「自动识别」）则上传即自动填好品类和全部字段，
  用户只做**扫一眼**。识别失败一律静默退回默认值模式，不阻塞录入。
- **一键导出 JSON/CSV** 常驻。你的数据永远属于你。

## 屏 1 · 今日（首页，唯一高频屏）

```
┌───────────────────────────┐
│  9月20日 周日 · 22℃ 多云   │
│  通勤 ▾                    │
├───────────────────────────┤
│                           │
│   ┌───────────────────┐   │
│   │                   │   │
│   │   一套搭配拼图     │   │  ← img_mask 本地合成
│   │  （上装/下装/鞋/   │   │     色系一眼可见
│   │    外套平铺合成）  │   │
│   │                   │   │
│   └───────────────────┘   │
│                           │
│  深灰开衫 · 米白衬衫 · 藏蓝直筒 │
│  · 棕色乐福鞋              │
│                           │
│  「色系统一，轮廓干净，         │
│    适合今天这种半正式的场合」  │  ← 模型给的理由
│                           │
│      ↑ 跳过      ↓ 就穿这套    │
│        长按 = 别再推这套       │
├───────────────────────────┤
│  ○ ○ ● ○ ○    第 3 套 / 5  │  ← 本轮已生成 5 套
├───────────────────────────┤
│ [ 换一批 ]      [ 自己搭 ]   │
└───────────────────────────┘
```

**交互定义（关键，别搞错）**

| 手势 | 语义 | 权重更新 |
|---|---|---|
| **下滑** | 今天就穿这套 | `alpha += 1.0` 最强正信号 |
| **上滑** | 跳过，没兴趣 | `beta += 0.3` 弱负信号 |
| **长按 / 双击** | 别再推这套 | `beta += 1.0` 强负信号 |

**把"今天不想穿"记成"不喜欢"，权重两周就脏了。这四个语义必须分开。**

**为什么显示"第 3 套 / 5"而不是只给一套：** 前两周是信任建立期。第 3 天撞上一套你觉得难看的，你会关掉通知再也不打开。先给 5 选 1，等你大概两周后信任它了，再收敛成每日一套。

**底部两个出口：**

- **换一批** — 重跑本地打分，不再调模型（省钱）
- **自己搭** — 手动选几件，让引擎判定"今天这温度这套行不行、要不要换双鞋"。**这是顾问模式，早晨最烦的不是"没想法"，是"有想法但不确定"。**

## 屏 4 · 新衣试穿间（V1 核心，差异化所在）

**这个屏从 V1 就要做，不等 V2。** 冷启动那两周你只有 20 件衣服，每日推荐的价值本来就有限；但买前模拟从录够基础衣橱那天起就能产生价值 —— **它是这个 App 里最快回本的模块。**

### 4.1 主屏 · 单件评估

```
┌───────────────────────────┐
│  新衣试穿间        候选 3 件  │
│  拍照 / 粘贴链接 → 影子录入   │
├───────────────────────────┤
│  [ 标准图 ]  卡其色直筒裤     │
│  ⚠ 主色取自商品图 · 置信 0.6  │
├───────────────────────────┤
│  「你缺『直筒通勤裤』这个位置」│  ← hole_flag=1 时改口径
│                           │
│  新增搭配   +12 套           │
│  覆盖季节   春 / 秋 / 冬      │
│  替代率     0               │
│  救活       1 件             │
│  净收益     +12             │
├───────────────────────────┤
│  能和谁搭（按贡献排序）        │
│  白衬衫  +9    藏蓝针织  +7   │
│  米白T恤 +6    棕色乐福鞋 +5  │
│  [ 看关系图 ]  [ 看全部 14 套 ]│
├───────────────────────────┤
│  ⚑ 救活：短款针织（原本孤岛）  │
├───────────────────────────┤
│  「能新增 12 套，替代率 0，   │
│    救活 1 件 → 建议买。」     │
├───────────────────────────┤
│  进一件出一件                │
│  推荐淘汰：厚底靴 (ΔN = 1)    │
│  [ 接受 ]   [ 忽略 ]         │
├───────────────────────────┤
│  [ 对比其他候选 ]            │
│  [ 确认买下 → 转入在库 ]      │
└───────────────────────────┘
```

### 4.2 子屏 · 横向对比（真实购物场景）

**电商大促你通常是在 3 件里选 1 件，不是"买不买"。**

```
┌───────────────────────────┐
│  候选对比 · 同一次想买 3 件    │
├───────────────────────────┤
│            A      B      C  │
│  新增     +12    +11    +10 │
│  救活      1      0      2  │
│  替代率    0      2      0  │
│  覆盖季节  3      2      3  │
│  单价    ¥299   ¥199   ¥359 │
├───────────────────────────┤
│  → 选 C：救活 2 件、替代率 0  │
│    A 次之。B 与现有重复，不买  │
└───────────────────────────┘
```

**同一件商品的多个颜色也能这样比。** 卡其 / 黑色 / 藏蓝三个颜色一起录，直接算出哪一色最值 —— 这件事只有这套系统能算。

### 4.3 设计要点

- **候选件是影子单品**（`stage='candidate'`），**绝不参与**衣橱效率、CPW、孤岛枢纽、每日推荐的统计。否则你录了 5 件候选还没买，App 会告诉你衣橱效率涨了。
- **关系图是主视图，指标卡只是辅助。** 你真正想看的是"能和谁搭"，不是四个数字。
- **`⚠` 标注低置信字段**，点一下可实时重算 —— 「如果主色其实是深卡其呢？」
- **「确认买下」是一键状态迁移**：`candidate → owned`，同时可选执行淘汰（进一件出一件）。
- **别问模型"这件配不配"**：模型是讨好人而不是拦人的，它会倾向回答"可以搭"。这一屏全部是**算出来的硬数字**。
- 候选件只有商品图时颜色会偏，**决定买之前用自然光拍一次实物核验**，或至少事后修正 `color_hex`。

**进一件出一件 —— 极简衣橱的本质是守恒，不是递减。**

## 版本切分

| 版本 | 内容 | 判断标准 |
|---|---|---|
| **V1** | 屏 0 录入 + 屏 1 今日（滑动）+ 屏 2 体检 + **屏 4 新衣试穿间** | 能连续用两周不烦，且录够 20 件就敢用它拦下购买 |
| **V2** | 屏 3 单品详情 + 屏 4 横向对比 + 同款多色对比 | 已经在拿它做购买决策 |
| **V3** | 屏 5 旅游打包 + 每日推送 | 日常已经在依赖它 |

**先把 V1 用满两周再动 V2。** 单人项目的死因从来不是功能少，是第 20 件衣服时不想录了。

**为什么买前模拟排在 V1 而不是 V2：** 它的价值不依赖数据积累 —— 只要有 20 件衣服就能算。每日推荐相反，它要靠几十次滑动才能建立信任。**先做那个第一天就有用的模块。**

## 冷启动流程（第一次打开）

1. 勾选风格标签（极简 / 日系 / 美式复古 / 机能 / 商务休闲）— 10 秒
2. 标 3–5 件"本命单品"（高频穿、喜欢穿）— 1 分钟
3. 拍 20 件最常穿的衣服，跑一遍录入 — 半小时
4. 首页当场给方案
5. **新衣试穿间同时解锁** — 走到第 3 步就已经能用了。这是整个 App 最快产出价值的地方

**前 20 次滑动几乎没有信息量**，前两周走**探索模式**（推得杂一点，多收集信息），之后切利用模式。这是标准的多臂老虎机问题，别指望第一天就懂你。

**别做"导入网图做风格画像"。** 那些图里的衣服你没有，提取出的风格特征无法落地成你衣橱里的具体组合。真画像来自两个更强信号：本命单品 + 给搭配打分。
