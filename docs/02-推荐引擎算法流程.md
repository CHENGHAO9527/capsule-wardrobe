# 推荐引擎算法流程

## 总原则

| 谁干 | 干什么 | 为什么 |
|---|---|---|
| 硬规则（代码） | 判物理可行性 | 错了是穿出门难看的物理错误，写死比交给模型稳定一百倍 |
| 本地权重 | 排序 | 用你自己的历史偏好，比模型通用审美更懂你 |
| 大模型 | 只在 Top-K 里做**选择题** + 给理由 | 让它生成它会编你根本没有的衣服 |

**铁律：所有输出必须 100% 由已有单品组成。永不输出"建议你买一件卡其色风衣"。**

---

## 阶段 0：录入与标准化（离线，一次性）

```
原始照片 → L0 拍摄规范 → L1 几何归一化 → L2 光学归一化 → L3 四输出
                                    ↓
                       视觉模型批量打 6 字段
                                    ↓
                          人工纠错 1–2 小时
```

视觉模型只负责**初稿**，用户点几下确认。让人从零打标签，第 20 件就崩了。

---

## 阶段 1：建图 `build_graph()`

```
节点 = 单品（仅 status='in_wardrobe'）
边   = 两件在某个合法组合中共存的可能性
```

边不必预存。80 件 → 3160 对，实时判定是毫秒级，不建缓存表。

---

## 阶段 2：硬规则 `is_compatible(a, b, ctx)`

**通用规则（全部硬编码）**

```
R1  同槽位不搭                     —— L4 不能配 L4，ACC 除外
R2  温度区间必须相交               —— 且并集须覆盖当天温度 ± 容差
R3  正式度差 ≤ 2                   —— 且整套极差 ≤ 2
R4  两个高饱和色不搭               —— 饱和度 > 0.5 且色相差 > 90°
R5  中性色无限兼容                 —— is_neutral=1 跳过 R4
```

**叠穿附加规则（只在多层路径生效）**

```
D1  厚度单调      沿 L1→L3 非递减（内薄外厚）
D2  领型兼容      高领内搭 + 翻领衬衫冲突
                  圆领内搭 + 开领外套永远成立
D3  长度关系      外套下摆 ≥ 内层下摆（按 length_band 排序比较）
D4  同层不叠      同 slot 只能出一件
D5  正式度单调    L3.formality ≥ L2.formality ≥ L1.formality
D6  袖型          短袖内搭 + 长袖外套：永远安全
                  长袖 + 长袖：仅当 sleeve='可卷' 时成立
```

**唯一的软规则 —— 交给模型**

```
S1  体积与轮廓：宽松叠宽松到底成不成立
```

前六条错了是物理错误；S1 错了只是没那么好看。**这就是规则与模型的边界。**

---

## 阶段 3：枚举合法路径 `enumerate_outfits(temp, occasion)`

```
输入：温度 T、场合 occ、可用单品集合（已过滤 status）

层数由温度决定：
  T ≥ 24°C        走 L1 → L4 → L5              两层
  14 ≤ T < 24     走 L1 → L3 → L4 → L5         三层
  5 ≤ T < 14      走 L1 → L2 → L3 → L4 → L5    四层
  T < 5           必须含 thickness ≥ 4 的 L3    强制加厚

DFS，每下一层立即校验 is_compatible，不合法就剪枝
不枚举全部组合，只枚举通过硬规则的路径  ← "有效搭配"的真义

ACC 层最后可选挂载，不计入路径枚举，只加成对校验
```

**复杂度控制：** 剪枝后实际枚举量通常几百到几千条，本地毫秒级完成。

---

## 阶段 4：本地打分 `score(outfit)`

```
score = w1 · 单品权重均值
      + w2 · 属性权重均值
      + w3 · 结构权重（该组合命中的 pattern_key）
      - w4 · 成对冲突惩罚        ← w_pair 后验
      + w5 · 新鲜度              ← 该组合 14 天内未出现加分
      + w6 · 场合匹配度
```

各项权重见 `settings` 表，可调。冷启动前 20 次走**探索模式**（`explore_ratio` 调高，故意推得杂一点收集信息），之后切**利用模式**。

取 Top-K（K ≈ 5）进入下一阶段。

---

## 阶段 5：模型判决（唯一花钱的一步）

```
发送内容：
  ① 候选 3–5 套，每套的结构化描述（品类/颜色/正式度/厚度/领型）
  ② 每套的 img_llm 图片（只发候选，每天最多约 15 张）
  ③ 当天温度、场合
  ④ 风格画像 + 明确要避开的项

提问（选择题，不是问答题）：
  「这几套里哪套最适合今天的场合和温度？为什么？」

模型返回：
  选中套编号 + 一句理由
```

**为什么必须做选择题：** 所有选项都是真实的、合法的、来自你衣橱的。而让它从零生成，它会开始编你没有的衣服。

**成本：** 图片只发候选，每天 1–2 次调用，一年几块钱。

---

## 阶段 6：理由反哺权重（白拿的收益）

模型说"这套好是因为色系统一" → 写入 `w_attr(color, 该色系)`
模型说"这套的比例更舒服" → 写入 `w_struct(tight_top_loose_bottom)`

**等于免费获得了一个审美老师的判断标准。**

## 阶段 7：反馈回灌 `learn()`（每夜重算）

### 7.1 手势 → 权重

```
accepted   (下滑)  alpha += 1.0
auto_worn  (实穿)  alpha += 1.5   最强信号
skipped    (上滑)  beta  += 0.3   弱负信号
rejected   (长按)  beta  += 1.0   强负信号
```

**必须区分 skipped / rejected。** 把"今天不想穿"记成"不喜欢"，权重两周就脏了。

### 7.2 信用分配 —— 一套 4 件被拒，到底在拒哪件

**方法一 · 频率法**
跨几十套被拒组合，统计哪件反复出现 → 大概率是它。

**方法二 · 条件概率（净贡献）**

```
贡献(A) = P(接受 | 含 A) − P(接受 | 不含 A)
P 用 Beta 后验均值，样本不足自动趋近 0.5（不误伤）
```

**方法三 · 成对冲突（最值钱）**

```
若  接受率(A) 高  且  接受率(B) 高  但  接受率(A∪B) 低
则  冲突不在 A、不在 B，在 (A, B) 这一对
→ 写入 w_pair(beta += 1)
```

**你的滑动手势真正的价值在这里。** 它学的不是"你喜欢什么单品"，而是"**哪些单品不能放在一起**"。这个知识任何现成 App 都没有——它们只做协同过滤，推"别人也这么穿"。

### 7.3 重算策略

数据量小（几千条反馈），**全量重算**即可，毫秒级。不做增量，不做复杂调参。

## 阶段 8：衣橱体检指标（第二屏）

### 8.1 衣橱效率

```
效率 = 有效搭配数 N / 在库单品数
串成一条线的衣橱 ≈ 1.4     磨过的胶囊衣橱 ≈ 8–10
```

首页大数字。它每天替你说一句人话：你的衣橱到底是不是衣橱。

### 8.2 孤岛件 / 枢纽件

```
ΔN(i) = N − N(移除 i 后的 N)

孤岛件   ΔN = 0       删掉它，组合空间损失为零
枢纽件   ΔN 最高      白衬衫删掉直接崩 40%
```

**该扔的是孤岛件，不是"看起来旧"的那件。大多数人扔错了东西。**

### 8.3 CPW（单次穿着成本）

```
CPW = purchase_price / wear_count
```

800 块穿 40 次的外套（CPW 20）吊打 200 块穿 3 次的爆款（CPW 67）。
极简衣橱唯一的量化终点。这个数字会直接改变你的购买行为。

## 阶段 9：买前模拟器（V1 核心模块，全市场空白）

**这个功能从 V1 就做，不等 V2。** 理由很实在：冷启动那两周你只有 20 件衣服，每日推荐的价值本来就有限；但买前模拟从录入够基础衣橱那天起就能产生价值 —— **它是这个 App 里最快回本的模块。**

依赖链：**录入 → 建图 → 买前模拟才成立。** 没有衣橱数据，这个功能一行都算不出来。

### 9.1 候选态隔离（数据模型的硬要求）

候选件必须是**影子单品**：`stage='candidate'`，**绝不参与**衣橱效率、CPW、孤岛枢纽、每日推荐的计算。

所有统计一律只跑 `stage='owned' AND status='in_wardrobe'`。否则你录了 5 件候选还没买，App 会告诉你衣橱效率涨了 —— 口径就脏了。

### 9.2 主流程

候选件照片走**同一条**标准化管线、**同一条**硬规则判定，但只放在衣橱外面做模拟，不写入 owned。

```
N_base = 当前衣橱的有效搭配数
N_with = 衣橱 + 候选件 的有效搭配数
ΔN     = N_with − N_base
```

### 9.3 ΔN 单独用会骗人 —— 空洞效应修正

**你衣橱里没有大衣 → 任何一件大衣录进来，ΔN 都会大得吓人。** 那不是这件大衣的功劳，是你的衣橱有个洞。

```
若 该槽位同类在库件数 = 0
   → hole_flag = 1
   → 输出口径改为：「你缺的是【大衣】这个位置，不是这一件。」
   → 强制切换到横向对比模式（同品类候选放一起比）
```

**这一条决定这个功能是帮你还是害你。** 不做修正，它会退化成一台"什么都值得买"的机器 —— 因为每件候选都能填补某种空缺。

### 9.4 搭档清单（主输出，不是四个数字）

用户真正想看的是"能和哪些衣服搭"，所以主输出是**以候选件为中心的关系图**，不是指标卡。

```
candidate × 每件 owned 单品 → 逐对跑 is_compatible（含 D1–D6 叠穿规则）

分组输出：
  核心搭档    贡献 ≥ 3 套新增组合
  普通搭档    贡献 1–2 套
  冲突件      判定不兼容，标出原因（撞色 / 撞正式度 / 温度不交 / 同槽位）
```

每个搭档标注它贡献的套数，点进去能看具体是哪几套搭配。

### 9.5 救活数（新件最独特的价值）

```
救活数 = 候选件加入后，原本 ΔN = 0 的孤岛件中被激活的件数
revival_ids = 这些单品的 id 列表
```

**一件衣服真正的溢价不在"锦上添花"，在把死件变成活件。**

例：衣橱里躺着一条高腰阔腿裤，配什么都不对，ΔN = 0。进来一件短款针织衫，它自己新增组合可能只有 3 套，但它把那条裤子救活了。

**这个指标任何现成产品都算不出来，因为它们不做孤岛分析。**

### 9.6 四个硬数字

```
① 新增组合数   ΔN
② 覆盖季节数   候选件参与的组合分布在几个温度带（春/秋/冬）
③ 替代率       能顶掉的同槽位现有件数
               （判定：移除该现有件，N 的下降量 < 候选件带来的增量）
④ 净收益       ΔN(候选) − ΔN(被淘汰件)
```

### 9.7 决策门槛（防止"什么都值得买"）

**没有门槛，每件候选都能新增组合，你会觉得什么都该买。** 所以必须写死判定：

```
建议买（满足任一）
  A  新增 ≥ 8 套  且  替代率 = 0  且  救活数 ≥ 1
  B  净收益 > 0   且  覆盖 ≥ 2 个季节
  C  替代率 ≥ 1   但  净收益 > 0（以旧换新，等价或升级）

建议对比（hole_flag = 1 时强制）
  同品类 ≥ 2 件候选 → 横向比，不给绝对结论

建议不买
  · 新增 < 3 套
  · 替代率 ≥ 2 且 净收益 ≤ 0
  · 与现有 3 件以上功能完全重叠
```

输出始终是一句人话：

> 「这条裤子能新增 12 套，替代率 0，救活 1 件 → 买。」
> 「新增 2 套，且和你已有的 3 条深蓝牛仔重复 → 不买。」
> 「你缺大衣这个位置，但这件只比 B 候选多 1 套 —— 先看 B。」

### 9.8 横向对比模式（真实场景）

**电商大促你通常是在 3 件里选 1 件，不是"买不买"。** 所以用 `eval_batch_id` 把同一次想买的几件绑成一组：

```
候选 A / B / C × (新增组合 · 救活数 · 替代率 · 覆盖季节 · 单价 · CPW 预估)

输出：「A 和 C 都能新增 10+ 套，但 A 替代率 2、C 替代率 0 → 选 C」
```

**同款多色也能这样比。** 同一件商品的卡其 / 黑色 / 藏蓝三个颜色一起录，直接算出哪一色最值。这件事只有这套系统能算。

### 9.9 进一件出一件

极简衣橱的本质是**守恒**，不是递减。

```
买条件：ΔN(候选件) > ΔN(被淘汰件)
```

模拟结果里直接给"推荐淘汰"清单（ΔN 最低的在库件），一键执行。**这条规则一旦跑起来，衣橱会自己收敛，不需要靠意志力。**

### 9.10 一个诚实的坑

候选件通常只有一张商品图，字段是**估的**：`field_conf` 记录每个字段的置信度。

- **主色**受商品图打光影响可能偏色 → 建议在自然光下拍实物，或在决定买之前核一次
- **正式度 / 温度区间**是主观估计，置信度天然低
- **四个数字全部建立在字段准确之上** —— 一张糊的商品图会给出错误建议

所以低置信字段旁必须标 `⚠`，并允许"如果我把它改成 XX，再看一次"的实时重算。

**这是所有竞品都没做的事。** 它们只能定性说"能搭几件""会不会重复"。没人给你一个硬数字 —— **因为商业产品的收入来自让你买衣服，没有人有动机做这个功能。**

## 阶段 10：旅游打包（集合覆盖，不是"搭 10 套"）

```
输入：天数 D、目的地温度带、场景集合（观光/正式晚餐/海边/徒步）

目标：最少件数覆盖最多场景

算法：
  1. 为每个场景生成合法搭配集合
  2. 贪心 + 局部搜索：每次选边际覆盖率最高的单品
  3. 输出双份结果

输出：
  ① 打包清单      核心 5 件 + 变体 3 件
  ② 每日穿搭矩阵   D 天 × 每套由哪几件组成
```

**用户看到的不是 10 套衣服，是 8 件衣服撑起 10 天。** 这个视觉冲击才是卖点。

## 附：CPW 与效率的正确解读

这两张表最容易误导自己，两条防线：

1. **CPW 需要足够的观察期。** 买了三个月的高价单品 CPW 必然难看。看它，但别在头三个月做决策。
2. **效率不是越高越好。** 效率 20 说明衣服高度同质化（十条一样的黑裤子），搭配空间是假的。**效率要配合"组合多样性"一起看**——即 N 里有几套是真正不同的色系/轮廓。
