# 胶囊衣橱

一个自用的**衣橱组合优化器**。目标不是「推荐穿搭」，是**用最少的衣服搭出最多的效果** —— 并且在你掏钱买下一件之前，算出它到底值不值。

## 已实现（V1 最小闭环）

**录入 → 建图 → 新衣试穿间。** 这条链路**不需要大模型**，全部是硬规则 + 图算法，纯本地跑：零 API 成本、零隐私风险、零网络依赖。

| 页面 | 地址 | 干什么 |
|---|---|---|
| **今日（首页）** | `/` | **自动取当天天气填好温度**（顶栏一行温控条，只有一个大数字），给你 **3 套今天能直接穿出门的搭配**，附理由。穿完点「就穿这套」。下面单独一张卡列出**你自己搭的套装**里今天能穿的那几套。**出门那几天可以开「旅行模式」** —— 只从那趟箱子里的衣服里挑，不用再一件件点「洗了」把没带的排掉。⚠️ 每件衣服上有**两个按件动作**：「**洗了**」= 这件今天不参与，「**不喜欢**」= 这件本身不喜欢（**按件记，不是按套**；累计多次会在体检页提示淘汰）。两个都是"减号"但代价不同，**用颜色和竖线分开**，别让手指点错。**「调」面板里可以「围绕某件搭」** —— 挑一件你喜欢的，只出含它的组合；穿完还能点**偏冷 / 偏热**，那调的是**你的舒适线**（不是某件衣服的厚薄，理由见 `app/feel.py`）。「换一批」是**硬排除已经看过的组合**，不是随机抖一下 |
| 录入工作台 | `/wardrobe` | 拖一批照片进来 → **槽位点一下就入库**（配了模型则全自动） |
| **计划（一周 / 旅行）** | `/plan` | 在家排一周（每天不重样）；出门排一趟（**逐件试删，能不带就不带**）。旅行可以**分段** —— 一路待两个地方也只有一个箱子。「常用」里存着**搜过的城市**和**搭过的行程**，点一下回填、天气现查 |
| **套装** | `/sets` | 自己从衣橱里挑一整套存下来，**之后今日页到了能穿的温度会自己端出来** |
| 新衣试穿间 | `/prebuy` | 候选件影子录入 → 算 ΔN / 救活数 / 替代率 → 给买不买。⚠️ **「厚度」常驻在卡片上**，不是藏在「改字段」里 —— 它最影响结论，而模型看图最容易把它估偏；估偏了就判「不买」，用户必须能当场改回来 |
| 衣橱体检 | `/stats` | 衣橱效率、各温度带搭配空间、枢纽件、孤岛件、CPW 排行，以及**「待淘汰观察」**（出现在被你点过「不喜欢」的搭配里最多的那几件 + 删掉会损失多少组合）。月报性质，不用天天看 |
| **接模型** | `/settings` | 视觉识别 + 审美排序的模型配置。见下 |

今日页支持深链，排查和收藏都用得上：`/?temp=23&occ=通勤`。

还没做：图片抠图标准化（现在是裁边 + 4:5 归一化）。见 `docs/03-V1界面结构.md` 的版本切分。

## 天气：直连 open-meteo，**不经大模型**

在 `/plan` 或今日页设一次常住城市，之后「今日」那一屏自己就知道今天多少度。

> ⚠️ 天气**千万不要**去问大模型。大模型 API 不联网，问它"今天几度"它会给你一个
> 语法通顺、数字瞎编的答案 —— 而温度是整套搭配枚举的输入，编错一个数，全盘皆错。
> 天气走 `app/weather.py` 直连 [open-meteo](https://open-meteo.com)（免费、不要 Key、
> 认识中文城市名）。接大模型只影响「录入自动填」和「今日审美排序」，与天气无关。

- **取哪个温度**：预报给的是当天最高/最低，穿衣要的是"出门那会儿"。三档可选 ——
  早（=最低）/ 平均 / 午后（=最高），默认平均，今日页点一下就切。
- **缓存 30 分钟**，落在 `data/weather.json`；**一次取满 16 天**（今日页要 1 天、
  计划页要 16 天，否则来回切页会互相顶掉缓存、打两次网）。
- **断网降级**：有旧缓存就回退旧缓存并标「旧数据」；没设城市就就地给一个搜索框；
  全部失败也**不抛异常**（首页不能因为天气打不开）。任何一支都不编默认温度。
- **远期旅行查不到预报**（open-meteo 只到 16 天）→ 不猜，弹一个逐天温度选择器让你给。
  排布本身一点不打折。**多段行程要按段分别处理这个落差**（可能一段在预报内、一段在预报外），
  并且把**整趟的日期轴**一起给出去 —— 两段之间隔几十天时，"从某天起连续 N 天"推出来的日子是错的。
- **看别人城市的天气不改你的配置**：`weather.forecast_for()` 查目的地，常住城市一个字不动。

## 在哪接模型

**固定地址 `/settings`**（每个页面右上角都有「设置」直达）。选服务商 → 粘 API Key → 保存 → 测试连接。

> 这一条踩过坑：最初把配置面板折叠在录入页里，今日页的「去配置」跳过去**什么都看不到**。
> 接入入口必须是一个稳定、独立、直接能打开的地址，不能藏在折叠面板里。

内置 8 个预设（**推荐 DeepSeek**）：
**DeepSeek（`deepseek-flash`，V4.1-Flash 原生多模态）** / 智谱 GLM-4V / 通义千问 VL / 硅基流动 /
月之暗面 Kimi / 火山方舟 / OpenAI / 本地 Ollama。
配置存在**项目根** `llm.json`，`GET /api/vision/config` 只回传「有没有 Key」，不回传明文。
（2026-10-01 从 `data/vision.json` 搬过来的：放 `data/` 里的话，每次发布都被整个甩掉，
云上那份永远没 Key —— 手机上就会让你重配一次**电脑上早就配好**的东西。见《发到云上》。）

**为什么默认推荐 DeepSeek**：一个 Key 同时管「看图识别」和「搭配排序」，不用配两个服务商；
价格可以忽略（单张图 token 上限 1024，空闲时段输入 1 元/百万 token，识别一件约 0.2 分钱，
80 件初始录入总共不到两毛）；空闲时段（含整个周末）再减半。

> ⚠️ DeepSeek 的模型名要写 **`deepseek-flash`**。旧名 `deepseek-v4-flash` /
> `deepseek-v4-flash-vision-exp` 虽然还能调，但官方已经下线、请求转由最新 Flash 承接；
> 带日期的临时版本名（`deepseek-v4.1-flash-expires-on-0910`）**已经过期**。
> DeepSeek 的报错很直白，会直接告诉你可用模型名：
> `The supported API model names are deepseek-flash, deepseek-v4-pro`。
> 填了不支持图片的模型（比如 `deepseek-v4-pro`）会返回 400，代码里会把
> `does not support image` 翻译成人话提示。

> ⚠️⚠️ **DeepSeek 必须关掉「思考模式」（`no_think`，预设里已默认勾上）。**
> 它的思考模式**默认打开、强度默认 high**：模型会先把 token 花在一段思维链上
> （放在 `reasoning_content` 里），回答正文 `content` 就变成空字符串 ——
> 看起来像"模型没回应"，其实是 `max_tokens` 被思维链吃光（`finish_reason=length`）。
> **实测：不关 4/19 张图返回空；关掉 19/19 全过。**
> 分类这种任务本来也不需要思考，关掉更快更省（推理 token 按输出 4 元/百万计费）。
> 请求参数是顶层 `{"thinking": {"type": "disabled"}}`，**只对声明了 `no_think` 的预设发送** ——
> 别的服务商收到未知字段可能直接 400。
> ⚠️ **三处调用（识别 / 排序 / 计划总结）都要带。** 排序曾经漏了：思维链吃光 `max_tokens`、
> 正文返回空串、被 `except` 吞掉 → **"模型排过序"这个标签一直是假的**，
> 页面看起来一切正常，用户只觉得"大模型审美没跟上"。现在正文为空会明确报出来。

接了之后变什么：

| | |
|---|---|
| **录入** | 上传照片自动填好品类、正式度、厚度、温度区间、领型、材质、版型、图案 —— 一下都不用点 |
| **今日** | 硬规则算出的候选里，由模型挑出最好看的那套并给一句理由（`vision.rank_outfits`） |
| **不变** | 颜色仍然本地测量（模型的色值不可复现）；搭配仍然由硬规则枚举，**模型只排序不生成** |

不接也能用：录入时每件点一下槽位，今日搭配走本地排序。**识别失败一律静默退回这个模式，不阻塞录入。**

## 温度怎么算：26℃穿衣法则（2026-09-23 换的）

> 用户："差一度的穿搭就差这么多吗？是不是可以给每一件衣服一个基础温度，每天的穿搭
> 加上当日气温之后如果达到舒适温度就可以？如果是这样的话是不是可以只算上半身，
> 下半身只考虑搭配。" 后来他又甩来一篇小红书《26℃穿衣法则》—— **那就是同一件事**，
> 而且是人民日报 / 科普中国 / 央广网多源一致的老规则。

**公式**（一字不差就是法则原文）：

```
                      当日气温 + 衣物保暖值之和 = 体感舒适温度
```

原表：较厚羽绒服 9℃｜薄款羽绒服 6℃｜稍厚絮棉衣 5℃｜厚羊毛衫 4℃｜棉背心 4℃｜
抓绒 / 薄外套 3℃｜厚棉毛衫 2℃｜薄棉毛衫（薄秋衣）1℃。
法则没点名的品类按"相当于哪一件"折算，落在 `catalog.CATEGORY_DEFAULTS[...]["warmth"]`。

**三条判定**（`rules.item_temp_ok` / `stack_warm_ok`）：

| # | 判什么 | 怎么做 |
|---|---|---|
| ① | 够不够暖 | `气温 + Σ(上装保暖值) ≥ 舒适线` |
| ② | 会不会太热 | `气温 ≤ **最外层上装**的上限` |
| ③ | 下半身 | 各自区间双边成立，**不参与保暖加总** |

> ⚠️ **②只看最外层**。第一版拿"体感"去比**被盖住**那件的上限，结果是越冷越判不合法
> （8℃ 三层被判成体感 32℃ 超了 T 恤的 30℃，5℃ 反倒合法）—— **曲线非单调**。
> `test_warmth.py` 里那条"合法温度必须是连续区间"就是它的回归。

> ⚠️ **③ 是用户口径，不是物理**。裤子鞋子当然也保暖，但（a）他对这个的直觉就要求这样，
> （b）库里裤子的温度区间全是 0~32 / 5~28 这种宽区间，参与判定只会制造噪音。
> 它们仍然按自己的区间判"能不能穿"（防夏天棉裤 / 冬天凉鞋），只是不进那个加总。

**层数因此是"算出来的"**：`graph.layer_plan` 的必需层永远只有 `L1/L4/L5`，
中间层/外层一律"可选" —— 穿不穿外套由"这套够不够暖"决定，不再由日历决定。

### 换掉的是什么（以及为什么非换不可）

原来是**温度阶梯**：`≥24℃` 不许有第二层、`18–23℃` 最多叠两层、`<14℃` 把中间层/外层
改成**必需**。实测（27 件真实衣橱，逐度扫核心组合数）：

| 跳变 | 幅度 | 根因 |
|---|---|---|
| 24→23℃ | **+50%** | ≥24℃ 时 L2/L3 **整层移出候选池** —— 而库里衬衫标的是 10~25℃、灰褐拉链卫衣 12~24℃。**数据说能穿，规则不许。** |
| 21→20℃ | +64% | 卫衣 `temp_max=20`，21℃ 排除、20℃ 全进来 |
| **14→13℃** | **−81%** | `<14℃` 把 L2/L3 从"可选"改成"必需"，上衣栈 4 种塌成 1 种 |
| 5→0℃ | −100% | 衣橱真的扛不住（真实冬季缺口，不是 bug） |

**换完之后**（同一套衣橱，舒适线 22℃）：

| 温度 | 30 | 28 | 26 | 24 | 22 | 20 | 18 | 16 | 14 | 13 | 12 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 核心组合 | 72 | 168 | 168 | 256 | 288 | 252 | 252 | 72 | 64 | 32 | 0 |
| 上衣栈种类 | 1 | 1 | 1 | 2 | 4 | 3 | 3 | 1 | 1 | 1 | 0 |

剩下的起伏都能一句话解释（"这几度上某件衣服太热 / 不够暖了"），没有"日历上切一刀"那种。

### 舒适线是**可调的**，别写死

法则原文的 26℃ 是标给**儿童**的（怕冷、代谢不同）。同一套衣橱：

| 舒适线 | 这套衣橱能穿到 |
|---|---|
| 26℃（法则原文） | **17℃** |
| 23℃ | 14℃ |
| **22℃（默认）** | **13℃** |
| 21℃ | 12℃ |

这份衣橱的保暖值上限是 9℃（T恤 1 + 卫衣 4 + 皮衣 4），所以"能穿到几度 = 舒适线 − 9"。
**它存在 `data/prefs.json`，在「设置」页里能拖**（20 怕热 / 22 中间 / 24 偏冷 / 26 法则原文）。
改了它，今日推荐和计划页立刻按新口径算 —— `_CORE_CACHE` 的键里含 comfort，
`_l1_domain` 的缓存键也含它（少一个就会出现"改了设置没变化"）。

### 不够暖的时候要说实话，不能装死

低于"能穿到"的温度，今日页会**空掉**。这是本意 —— 这个产品的卖点是"买之前算出值不值"，
那就得敢说"你缺一件真正的外套"。但空态必须自证，所以 `Closet.diagnose` 多了一种：
`kind="too_cold"`，配一句

> 8℃ 下需要上装提供 14℃ 保暖（舒适线 22℃），而你所有上衣叠满也只有 9℃ ——
> 不是没有衣服，是缺一件真正的外套。

`Closet.max_top_warmth()` 用**上界**（max 内搭[排除只能单穿的] + max 中间层 + max 外层）：
上界都够不着需求，才敢断定"缺外套"。

### 保暖值怎么落到每件衣服上

- `items.warmth` 一个整型列（℃），**只有上装参与加总**，下半身恒 0；
- 默认值按品类给，在 `catalog.CATEGORY_DEFAULTS` 里，**录入选完品类就自动填好**；
- **每件都能改**：「录入」页「已入库」每一行右边点**「改字段」**，掀开一张只盖这一件的
  面板，里面就有「保暖值 ℃」（面板里同时还有槽位、品类、温度区间、按品类重置、删）；
- 老库靠启动时的 `_backfill_warmth()` 按品类补上（**只补 NULL，不覆盖你改过的**）；
- 字段为空时 `rules.warmth()` 按厚度兜底（1→1 / 2→2 / 3→3 / 4→5 / 5→8），
  **兜底值必须是确定性的**，否则"改了别的字段搭配就变"那种幽灵 bug 又会回来。

> ⚠️ 加这个字段要**同时**改六处（少一处就是静默失效）：
> `schema.sql` → `db._MIGRATIONS` → `ItemIn`（否则 `ITEM_FIELDS` 会把它丢掉）
> → `graph._FP_FIELDS`（否则改了保暖值搭配不变）→ `/api/meta`（前端要自动填）
> → `apitest` 读回来的断言。见 `test_warmth.py` 的 ⑥：它把这六处逐条钉住了。

## 今日推荐怎么算的

**硬规则枚举 → 本地打分 → （可选）模型做审美排序 → 落库。** 全程只有第三步花钱。

打分项：场合正式度贴合、色彩和谐（几个彩色、有没有中性色锚点）、温度适配、
**新鲜度**（最近穿过的降权）、**Beta 学习权重**、本命单品、刚被否掉的件重罚。
挑出来之后还要过一遍**多样性**：一套要跟已选的每一套至少差 2 件，
否则三套只是「换一双鞋」。

学习闭环是纯本地的，表结构早就留着（`w_item` / `w_pair` / `feedback` / `wear_log`）：

| 操作 | 写什么 |
|---|---|
| ✓ 就穿这套 | `w_item.alpha += 1.5`、`wear_log` 记一条、`wear_count += 1` |
| 换一批 | 当前这套记 `skipped`，`w_item.beta += 0.3` |
| 不喜欢 | 当前这套记 `rejected`，`w_item.beta += 1.0` |

后验均值 = α/(α+β)，**天生带样本量衰减**：被拒一次从 0.5 掉到 0.33（扣 6.7 分，够挤出前三），
但要攒到三次才真的压死一件衣服。手写百分比权重两星期就会被噪音带偏。

`w_pair` 是这套里最值钱的一张表：两件分别你都接受、但放在同一套里你总拒绝 →
**冲突在这一对，不在任何一件上**。首页底部的「它在慢慢懂你」会把这类冲突直接列出来。

> ⚠️ 写权重时注意：`INSERT ... ON CONFLICT DO UPDATE` 在**插入新行时不执行 DO UPDATE 分支**。
> 增量必须同时写进 `VALUES`，否则一件衣服的第一次反馈会被静默吞掉，β 永远停在 1.0，学习闭环根本不启动。

接了大模型的话，它只做一件事：**在候选里排序，并给一句话理由**（`vision.rank_outfits`）。
绝不重新生成 —— 让它生成，它就会推荐你根本没有的衣服。

### 排序提示词怎么写的（`vision.RANK_PROMPT`）

给模型的不是一堆形容词，是**能照着比的具体条目，而且排了先后**：

**轮廓 → 明度 → 色彩 → 材质厚薄 → 正式度 → 呼应**，前面分出了胜负就不用看后面。
顺序是刻意的：隔三米看，衣服的**形状**比颜色先被看见。
配一份**反面清单**（上下都宽松 / 三个以上彩色 / 图案打架 / 外套敞开就散架 / 厚薄断层 /
正式度割裂）—— 只告诉它"什么好"不够，模型需要一个**否定的把手**。
理由也必须说具体的（轮廓 / 明度 / 材质 / 呼应里的哪一条），**不许写"搭配协调"那种空话**。

输入侧同样重要：`_describe` 会喂 领型 / 袖型 / 衣长 / 版型 / 厚薄 / 图案 / 本命件，
外加一个**本地算好的明度档位**（`_lightness`）—— 判"明暗差"时，
文字模型看 `#6B7280` 是悬的，而颜色本来就是这个项目的本地活。

> ⚠️ 排序失败**必须看得见**。`rank_outfits` 返回 `{"used", "error"}`，
> 一路传到 `/api/today` 的 `llm_error`，页面上红字说明 + 标签变成「模型没回应」。
> 静默退回本地排序看着无害，实际会让人以为是"模型水平不行"（真发生过）。

## 自己搭的套装（`/sets`）

一句话：**自己挑的一整套存下来，今日页到了能穿的温度就自己端出来。**

和「搭配历史」不是一回事 —— `outfits` 是程序算给你的一次性结果（反馈挂在那上面），
`sets` 是你自己挑的、长期留着。所以今日页把它们放**单独一张卡**，**不占推荐的 3 个名额**。

三条设计：
- **不存温度区间。** 能不能穿一律**现算**（扫 -10~38℃，单点判定用 `can_wear`）。
  存了就会和引擎漂移：你改一件单品的温度，那个区间就悄悄过期了。
- **判定复用引擎枚举，不在旁边再写一套规则。** 否则会出现"套装页说能穿、今日页说不能穿"
  这种各说各话（"算不算换了一套"的口径、温度口径，都是因为写了两份而踩过坑）。
- **存下来的必须是能穿的**（不过就 400 + 一句人话原因）。存一套永远穿不出去的东西，
  只会变成今日页里一个永不出现的幽灵，用户还以为功能坏了。

动手时踩到的四个坑，两个是真 bug：

| 坑 | 后果 |
|---|---|
| `SetIn.item_ids` 默认 `[]` | **PATCH 只改个名字就把单品清空了**（返回 400）。改成"没传的字段一律保持原样"：`item_ids=None` = 不改，`occasion`/`note` 用 `UNSET` 哨兵区分"没传"与"要清空" |
| `pick_items` 在**已筛完的列表**里找缺失项 | `missing` **恒为空** —— 界面永远不会提示"少了 X 件"，不报错也不算数。两个返回值都要基于原始输入算 |
| `can_wear` 只看枚举 | ① 同槽位重复会被 `must={slot:item}` 静默压成一件 ② **28℃ 的方案里压根没有 L2/L3 两个槽** → "T恤+卫衣+夹克+裤+鞋"被判成能穿，多出来的两件被无声丢掉。**一套的意思就是"这些一起穿"** |
| 测试脚手架 `mk()` 忘了 `it.update(kw)` | 传进去的 `is_neutral=0`/`color_hex` 全被丢掉、假单品全成了中性灰 → "撞色不能存"几条断言失败，**看上去像产品 bug** |

点「今天穿这套」走 `/api/sets/{id}/use`：落一条 `outfits` 记录再挂 `auto_worn` ——
和推荐**完全同一条反馈路径**，所以 `wear_log`、单品穿着次数、Beta 权重都照常累加，
不会因为来源不同被漏掉。

自检 `scripts/test_sets.py` **全程跑内存库**（内存里建库 + 跑一遍 `schema.sql`）——
因为 `use` 会写用户真实的 `wear_count` / `wear_log`，在真实库上测就是拿穿着记录当试验田。

## 洗衣篮：今天洗了的件

一句话：**今日页每件衣服下面一个「洗了」，点完这件今天就不再参与搭配；推荐下方一条
「洗衣篮 N 件」把洗掉的名字列出来 —— 点名字放回单件，点「全部恢复」全放回来。**

三条不成文的规矩：

- **它是"真排除"，不是"降权"。** `avoid_ids`（那个 `exclude=` 参数）只是打分罚分 ——
  罚完这件照样可能被选中；而洗了的衣服是**物理上穿不了**。所以洗掉的 id 是从
  `items` 里直接剔掉的（`api_today` 开头那几行），不是塞进 `avoid_ids` 凑合。
- **它只管今日推荐。** 计划页的一周 / 旅行要按"你衣柜里有什么"排 ——
  它回答的是「**出门那几天这件在不在手边**」，而洗了回答的是「**今天这件干不干净**」。
  两个问题，答案不该互相污染。所以剔除**只发生在 `/api/today` 这一条路径**上，
  `app/plan.py` 里压根不该出现 `laundry` 这个词（`test_wash.py` ④ 会 grep 它）。
- **它是状态，不是属性。** 晾干就回来，明天它还是那件卫衣 —— 所以存在
  `data/laundry.json`（跟 `prefs.json` 一个路子），**不进 items 表**：
  进了表就会跟着单品进导出、进体检、进缓存指纹（`_FP_FIELDS`），
  变成一笔"要记得改回来"的数据债。

两处**必须**的兜底，少一个就是又一次静默失败：

| 场景 | 不做的后果 |
|---|---|
| 读取时跟当前衣橱**取交集**（`laundry.ids() & {...}`） | json 里存的是 id，单品删掉后 id 会残留 → 界面上出现一件**点不动的幽灵衣服** |
| 全洗了要走 `all_washed` 空态，**并且带上整份洗衣篮** | 洗光了 → 排不出来 → 首页上找不到地方点「恢复」，**用户被自己的操作关在门外** |

> ⚠️ 洗掉的件会让 `cores` 变小（那是"今天能算的组合数"，本来就该小），但响应里的
> `n_items` 仍然是**衣橱总件数** —— 拿剔除后的数去填副标题，看着就像"我的衣服丢了"。

自检 `scripts/test_wash.py`：把洗衣篮**指到临时目录**（不隔离的话，跑一次自检就把
用户正在洗的衣服清空了，而且不报错），然后拿真实的 `/api/today` 走一遍 ——
洗 1 件、洗一半、全洗、恢复，外加「计划页不受影响」那条**结构断言**：
不光比"跑出来一样"，还直接 grep `app/plan.py` 里不许出现 `laundry`。

## 一周 / 旅行怎么排的

两件事看着是两个功能，其实是同一个问题的两个方向：**在家要"不重样"，出门要"少带件"**。
共用一个引擎（`app/plan.py`）：**排布逻辑完全一样，旅行只多一步「逐件试删」**。
所有搭配照旧全部来自硬规则枚举，模型只写一句总结。

1. **每天各取一个候选池**（`_day_pool`）：按「看得见的组合」去重 ——
   上衣 × 下装 × 鞋，同一个组合只留打分最高的那套。
   截断时**先按上衣铺开再截**，每件上衣最多留 3 套，免得高分的那两件占满整个池子。
2. **贪心排布**：先排候选最少的那天（它最没得挑）。代价函数（`_cost`）比的是
   **`(保暖缺口, 其余代价)` 这个元组** —— 先把"穿得单薄"排干净，再谈好不好看。
   其余部分里"上衣重复"罚得最重（24 分），其次是"同一套原样又穿一遍"（8 分）
   和"裤子/鞋不换"（3.5 分）。
3. **旅行再加一步：逐件试删**（`shrink`）。把打包清单里的每一件拿出来问
   "不带它，这 N 天还能不能每天穿出**不一样**的一套" —— 答得出就真不让你带。
   **这一步才是这个功能真正值钱的地方。**
   但有两道闸（见下）：`_can_serve` 和 `_keep_floor`。
   **少带件归它管，所以排布的代价函数里不需要再"能省就省"** ——
   曾经给旅行单独写了一档"复用已有件算加分"的代价，结果它乐于七天穿同一条裤子、同一双鞋，
   手感很差。省件数是试删的活，排布只管排得好看。
4. **顺序不能颠倒：先修贴身层（`_repair_l1`），再试删，箱子定了重排一遍再修一次。**
   实测数据（7 天、白天 22~15℃、早晚 19~12℃）：**一周模式用到 16 件；
   旅行模式试删到 9 件（4 内搭 + 1 中间层 + 1 外套 + 2 裤 + 1 鞋），
   7 天上衣不重样。** 顺序反了的话，试删收到的是贪心排出来的**违规清单**
   （一件 T 恤穿 3 天），容量闸必然否掉所有尝试 → 一件都省不下来（详见下面那几条 ⚠️）。

### 先算「该带几件」，再排穿搭（2026-09-28）

用户原话：「穿搭还是有点太僵硬了：如果全部都默认的话，它可能只给我带一件中间的卫衣，
8 天甚至 10 天都只穿那一件，我觉得这很不合理。……是不是先判断一下，比如 10 天旅游
应该带多少衣服，然后再去做穿搭，而不是说最少带多少衣服」

**他说的是对的，而且这根本不是"调个参数"—— 是四层 bug 叠在一起，每一层都静默：**

1. **`WEAR_CAP` 只管 L1。** 内搭有"一件最多穿 2 天、不连穿"的规矩，**中间层（L2）没有** ——
   于是 10 天只带一件卫衣，引擎认为完全合规。
2. **L2 在代价函数里只吃到 60 分的"悬崖"，占不到便宜也吃不到亏。**
   悬崖的意思是：**所有候选都一样贵时它就失去了区分度** ——
   穿 2 天的和穿 10 天的同价，引擎自然随便挑一个。
3. **`_cost` 的 `comfort` 参数压根没被传进去。** `_greedy` 用**位置参数**调 `_cost`，
   漏了最后一个 `comfort` → 回落成 `DEFAULT_COMFORT = 22`，而用户的舒适线是 19
   → **"保暖缺口"整整算错 3℃**。
4. **候选池里的 `items` 是投影，里面没有 `warmth`。** `outfits.public_item()` 是给前端看的，
   **故意**不带 `warmth`（`thickness` 反倒留着）。拿它去调 `rules.warmth(...)`
   会**静默回落成"按厚度查表"**（T恤 1→2、米白卫衣 4→3），数字全错，一声不吭。
   修法：新增 `_cand_items(cand)` 取 `cand["path"]`（真实完整 dict），三处调用一起换。

修完之后照用户说的顺序来：**先算这件数，再拿它当试删的下限。**

- **按品类算，不按槽位。** `WEAR_CAP_BY_CAT`：L1 类（T恤/衬衫/薄针织/吊带/Polo 衫）一件 2 天；
  L2 类（毛衣/卫衣/针织开衫/马甲/厚衬衫）`L2_WEAR_CAP = 4` 天。
  **L3（外套）故意不设上限** —— 一件大衣连穿十天很正常，"因为它贵所以更该少带"是错的。
- **`_l1_need` / `_l2_need` / `_layer_need`**：`⌈N / cap⌉` 就是"这层至少几件"。
  `_keep_floor` 拿它当**试删的下限**，`shrink` 不许把中间层删到这个数以下。
  **这就是"先算该带几件"的落点**：不是不省件，是不许省到同一件穿十天。
- **平方罚（斜坡）替掉悬崖**：`cost += (4.0 if L1 else 20.0) * n²` ——
  穿得越多越贵，逼它去找那件**没穿过**的。平方项是**斜坡**（有区分度），
  60 分是**悬崖**（所有候选都踩上就退化成比分数）。
- **重复警告点名层**：不再写死"内搭"，按哪一层真顶到上限来说话。

**实测（真实衣橱，10 天行程）：**

| 档位 | 修之前 | 修之后 |
|---|---|---|
| 18℃ | 米白印花卫衣 ×10（一件穿满） | 米白 ×3 · 灰连帽 ×2 · 藏青连帽 ×2 …（3–4 件轮换） |
| 15℃ | 同上 | 米白 ×4 · 灰 ×3 · 藏青 ×3 |
| 12–13℃ | 一件中间层 | 4 件中间层 + 外套 |

### ⚠️ 修的正是"太少"，别顺手修成"太多"（2026-09-28 当天回访）

上面那一版发布当天用户就回来了：

> 「感觉好像有点矫枉过正，是不是现在带的衣服又太多了？像我 10 天左右的假期，如果出去玩的话，
> 我可能最多就是带两件外套、3 条裤子。内搭的话，短袖带得多一点，中间层带得丰富一点。
> 倒不是要带得多，但是不能只带卫衣吧」

**先量，再改。** 拿 5 档温度跑真实衣橱，10 天/7 天各看一遍每层件数 ——
结果外套**从没超过 1 件**、裤子**从没超过 2 条**，所以他说的"两件外套、3 条裤子"
是**心理上限**，不是他看到的超标。真正超标的是**中间层**：`L2_WEAR_CAP = 3` 时
一件最多穿 3 天 → 10 天要 `⌈10/3⌉ = 4` 件，而 L2 池子一共就 5 件 —— 等于**把中间层全带上了**。

**改一个数：`L2_WEAR_CAP` 3 → 4。** 10 天 4 件 → 3 件。
（`_l1_need` / `_l2_need` / `_keep_floor` / 警告文案全从这一个常量派生，改它一处就够。）

再看那 3 件是**哪 3 件**：

| 档位 | 中间层（改之前 → 改之后） |
|---|---|
| 10 天 18~22℃ | 格纹衬衫 · 牛仔衬衫 · 灰连帽卫衣 · 藏青连帽卫衣 → **格纹衬衫 · 牛仔衬衫 · 藏青连帽卫衣** |
| 7 天 14~25℃ | 3 件 → **2 件** |

——**从"一堆卫衣"变成"衬衫 + 卫衣"**。件数降下来之后，腾挪空间反而大了，
引擎自己就把品类摊开了（这也顺带说明：件数挤到极限时，多样性是**第一个被牺牲**的）。

### ⚠️ 内搭那 5 件，是"拿不出来"不是"带得不够"

同一轮发现的：温和档 10 天排出 **4 件内搭**，系统却警告
「10 天至少要有 **5** 件内搭，而且每天都得留得出别的选择」。

**用户会看到系统一边说不够、一边不给** —— 而这根本不是"带得不够"：

真实衣橱 8 件 L1 里，**5 件带标签**（4 件 `solo_only` + 1 件 `never_outer`）。
14~18℃ 要叠层时，`solo_only` 的件**当不了内搭** → 真正可用的只有 **4 件**，
而 `_l1_need(10) = 5`。**旧文案等于让用户去找一件他根本拿不出来的衣服。**

修法：`_greedy` 里数一遍**候选池里真出现过的内搭件数**（`_pool_l1`），
比 `_l1_need` 少就说"能当内搭的只有 N 件（标了「只能单穿」的一叠层就穿不上）"，
并给出下一步（**去「改字段」把标签改掉，或者再添两件**）。
`build_plan` 里那条兜底警告同样分岔（用 `cur_pools` 数）。

**「缺件」和「拿不出来」是两回事 —— 对用户的下一步完全不同**：
一个是往箱子里再塞一件，一个是去改标签/买新衣服。

### ⚠️ 一个查不到任何报错的静默失败：标记串和文案脱节

`plan.REPEAT_WARN_MARK` **不是给人看的文案，是给代码用的标记** ——
它被三处逻辑拿去"认自己那句话"：

1. `_repair_l1` 修好贴身层之后，按它把旧警告**撤掉**（留着就自相矛盾）；
2. 同上，第二道修补之后再撤一次；
3. `build_plan` 收尾的兜底：**已有这条警告就别再补一条**。

2026-09-28 发现它写的是 `"得重复穿某件内搭"`，而正文里实际是
`"得重复穿同一件了"` —— 一个**从来没在文案里出现过的字符串**。
于是三处逻辑**全部静默失效**：两条旧警告永远撤不掉，兜底永远认为是"还没有"。
用户看到的是同一件事说了**两遍**，而且其中一条已经过时。

**而且它几乎不可能靠读代码发现** —— 字符串比对一个反了也不会报错。

**这条静态看不住，得动态测**：`test_plan.py` 造一个"内搭被标签卡住、必然重复穿"的
合成衣橱，然后断言 `REPEAT_WARN_MARK` 在警告列表里**出现且只出现一次**：

- **0 次** → 标记和文案脱节了（正是本节的坑）；
- **2 次** → 同类警告没合并，或兜底没被抑制。

一个断言同时看住两种翻车方向。
⚠️ 所以**改这句文案时必须同步改常量** —— 判据是 `REPEAT_WARN_MARK in <文案>` 为真。
（写这一节的时候我自己就先踩了一次：为了"说重点"把"得重复穿同一件了"改成
"得重复穿"，常量没动 —— 幸好那条断言在。）


⚠️ **"必选衣服没搭进去"是另一条线**（`must_ids`）：手填温度那条路
（`#pkgo` / `#pkback`）自建 body 时漏了 `must_ids`，而它只在 `runOnce` 一处被设置 ——
"尼斯 / 巴黎"这种手动给温度的场景走的正是这条路。已补全三路（搜索 / 常用 / 手填）。

### 旅行可以分几段（2026-09-25）

用户原话：「**旅游那边如果我在两个不同的旅游地呢？**」

**引擎一行都没改，这是刻意的。** `plan.build_plan` 只吃一条按日期排好的温度序列
（`days`），里面**根本没有"城市"这个概念** —— 城市只在"温度从哪来"这一步存在。
而"少带一件"本来就是按「**整趟行程共用一份清单**」算的（试删问的是"不带这件，
这几天还排得出吗"），所以两段**天然合出一个箱子** —— 是必然，不是碰巧。

分段只加在 `app/main.py` 的 `_plan_weather_segments()` 和 `web/plan.html` 上：

- **页面上**：旅行模式的「去哪儿」变成一张分段列表 ——
  `① 京都 3 天 / ② 大阪市 3 天`，每段自己的天数（`select`），`共 6 天`。
  再搜一次城市就是**追加一段**（不是替换），按钮文案跟着变成「加一段」。
- **一段都没选时走老路**（按常住城市的天气排），一步没变。
- ⚠️ **分段之后「排几天」必须收起来**：天数是**每一段自己的**，也是唯一的状态源。
  页面里同时存在两个能改天数的地方 = 两个状态源，必然打架。
- **日期在这里算，后端不猜**：每段从开始日逐段往后推，`segments[i].start` 首尾相接。
- ⚠️ **日期轴必须显式给回去（`day_axis`）**，这是整件事最容易出错的地方：
  两段之间可能隔着几十天（10/01 京都、11/20 大阪），
  前端按"从某天起连续 N 天"推出来的日期是**错的**，
  而用户填完温度提交时用的正是这些日期。跨预报边界时（一段在 16 天内、
  一段在预报外）只把查得到的那几天给出去当预填，`day_axis` 依然给全部日子。
- 排布结果里每天带一个 `seg` 标签，**只在每段第一天**画一条段名（天天挂地名是噪音），
  依据卡里再给一条 `京都 7 天 → 大阪市 3 天 · 共 10 天` 的链。
- 自检：`scripts/test_plan.py` 的「④ 旅行分段目的地」（离线打桩，
  含跨预报边界与重叠去重）＋ `scripts/checkform.mjs` 的「旅行去两个地方」。

实测（2026-09-25，真实衣橱）：京都 7 天 + 大阪市 3 天 →
**10 天全排出来，一个箱子 9 件**，上衣不重样 9 天。

### 「常用」：搜过的城市 + 存过的行程（2026-09-28）

用户原话：「历史记录看不到，我每次只要有一点变动，再回到旅行界面，我就要重新输入城市、
重新输入时间，我觉得这个就很折磨人。」他要两件事：搜过的城市变快捷按钮；
搭过的行程（尼斯 4 天 → 巴黎 6 天）能一键回填、顺手更新气温。

- **存 `localStorage`，不进库。** `capsule.cities` / `capsule.trips`（最多 8 城 / 6 趟）——
  "你这个人在这个浏览器上的习惯"不是衣橱数据。
- **只存结构化字段，不存结果。** 一趟行程存 `[{label, city, lat, lon, days}, …]`，
  重排时天气**现查**。存了温度 = 存了一份会过期的答案。
- **`tripKey` 只按行程算，不含天数** —— 改天数就是覆盖那一趟，不占新的格子。
- **整趟换，不是追加。** 点存过的行程 → `segs` 整个替换 + 重排；
  点城市按钮 → **加一段**（第一段沿用「排几天」，追加段默认 3 天）。
- **排成功才记**（`rememberTrip()` 放在 `runOnce` 里清空结果之后）——
  排失败还记下来，等于把一次错误存成了"常用"。
- 自检：`scripts/checkhist.mjs`，8 组不变量（A 只在旅行模式出现 … H 同趟覆盖不新增），
  **真开浏览器、真派发点击**：点城市按钮真的加了一段、点行程行真的把两段换回来、
  点「×」真的只删那一趟。它自己踩过一个坑：断言原来按**下标**取 `[data-trip]` 第 0 行，
  而 D 段刚点出来的单段行程会排到最前 —— 功能完全正常，是断言在依赖"列表里恰好只有一趟"。
  **按名字找行**才对。

### 五条口径（2026-09-21 按用户反馈定的）

**① "算不算换了穿搭"看上衣。** 用户原话："同样的搭配只是换一条同样颜色的裤子这个逻辑总觉得
很奇怪，从我自己来看我觉得换上衣才算是换穿搭。" 所以跨天去重的单位是**上衣栈**
（`_look`：L1/L2/L3 那几件的组合），不是 `graph.core_of` 的核心 ——
核心只取"最外层上装"，T恤+皮衣 换成 灰T+皮衣 它纹丝不动，正是被吐槽的"只换了条裤子"。
**体检页的主指标仍然用核心**（那是"衣橱能少到几件还穿得出几种样子"），两者不要互相改。

**② 贴身层有穿着规矩。** 内搭一件最多穿 2 天、且不连穿两天（用户原话："短袖基本不会连续穿两天"）。
这不只是观感问题 —— **它是"旅行 7 天只带一件 T 恤"这个荒唐结果的唯一拦路虎**：
试删只会问"每天还能不能有得穿"，不问"七天穿同一件 T 恤像话吗"。
规矩写在代价里（60 分，重到"只要还有别的选择就不会落上"）而不是硬过滤：
内搭实在不够时，用户该看到的是"某天不得不重复穿"这句实话，而不是"这天排不出来"。

**②′ 光靠代价不够，排完必须回头再修一遍**（`_repair_l1`）。
`_greedy` 是逐天决策的，而且处理顺序按"哪天候选最少"排 —— **它看不到全局**。
实测 7 天旅行：轮到最后一两天时 4 件内搭全都到上限了，它只能违规，
排出一件 T 恤穿 3 天（还连穿了）。而这件事**有解**（`_l1_need` 已经保证件数够），
只是需要回头改前几天。做法：整批排完之后，拿每天候选池里的内搭当域，
跑一次回溯（`_solve_l1`，跟试删共用同一套判定）求一份合规排班，再按排班把内搭换掉。

> ⚠️ **域必须收窄到"那天保暖缺口最小的那批候选"。** 用全部内搭当域，
> `_solve_l1` 会给出"数学上成立、落地时落不了"的排班 —— 它让 15℃ 那天换成某件内搭，
> 而那件在那个池子里只出现在**单穿**的套里。实测就是这么差一步没修好（改了两处、
> 剩下那处还是穿 3 天）。收窄之后，域里每一件都有"穿得住"的落地方式。
> ⚠️ **修完要拿最终结果复核**（`_l1_issues`）：只改得动一部分时，若因为"改过几套"
> 就把提示撤掉，那就是又一种静默失败。交换时再兜一道"保暖缺口不许变大" ——
> 宁可重复穿，也不能冻着（第一版没这条，直接破坏了 14/16/18℃ 的"穿够两层"）。
> ⚠️ **现状没违规就别动手**（`_l1_issues` 空就直接返回，2026-09-22 补）。
> `_solve_l1` 只要求"存在一份分配"，**不比较"是不是比现在这份更好"** —— 哪怕当天排得
> 好好的，它也会给出另一份合法方案，然后逐天照换；而换的那套是从池子里重挑的，
> 于是 `_greedy` 刚排好的裤子轮换被无声推翻（实测：7 天排成 7 条不同的裤子，
> 这一趟换成同一条穿 5 天）。**救火的步骤不该顺手改别的东西。**
> 同理 `_pick_with_l1` 的排序加上了下装/鞋的重复代价，口径与 `_cost` ③/③′ 同源 ——
> 两边各算各的，就会互相拆台。

**③ 温度低就不许只穿一件 —— 现在**归引擎**管（2026-09-23 换模型后）。**
用户原话："18 度怎么可能只穿短袖"。以前这条是排布层的一个罚分（下面的历史记录还在），
现在 `rules.stack_warm_ok` 在叶子上就把"不够暖"的组合否掉了，排布根本拿不到那种候选，
`WARM_LINE` / `WARM_MIN_TOPS` / `_warm_gap` 三个常量随之**删掉**。
理由：那条线原本有两份（引擎的温度带 + plan 的 20℃），迟早漂移 —— 事实上它已经漂移过
（今日页允许 18℃ 单穿短袖，而计划页在罚它）。现在**门槛只有一处**：`prefs.comfort()`。
详见下面《温度怎么算：26℃穿衣法则》。

> 历史记录（当时为什么这么做，避免重蹈）：
> 引擎允许"不穿外套"是刻意的（23℃ 不穿很正常），但它不会主动替你想"18℃ 出门要加一件" ——
> 而代价函数里**加一件外套只会**被"引入新件 +1.5"罚分，"穿得太单薄"完全没人管，
> 排序就向着少穿一件去了。当时的修法是：低于 `WARM_LINE`（20℃）时把上装件数当**排序第一关键字**
> （字典序，不做加权加法 —— 重复惩罚是累加的，实测 18℃ 的旅行里重复到第 4 次累到 48 分，
> 反超了 45 分的缺口罚分）。
>
> **试删那一侧**（`_keep_floor("TOP")` + `_toppers_warm_enough`）**保留着**，
> 但判据换成 26℃法则算出来的"光靠内搭够不够" —— 它管的是"箱子里要不要留一件能加的"，
> 跟引擎的逐套判定不是一回事。

**④ 内搭要摊开穿（`_cost` 里的平方惩罚）。** 贪心看不到后面几天：
7 天、箱子里 4 件内搭时，它每天挑"当前最顺眼"的那两件，到第 6 天发现三件都用满 2 次、
第 4 件一次没轮到 —— 而它在每天的候选里都只差一点点分数，**那天于是无解，只能违规**。
平方让"穿过的"比"没穿过的"贵一点（0→0、1→4、2→16、3→36），内搭就自然轮着来。
外套不算 —— 一件夹克穿一周是正常穿法。**裤子和鞋同理但力度不同，见 ④′。**

**④′ 裤子和鞋各自摊开穿（2026-09-22 按用户反馈补）。**
用户原话："这怎么选了一条裤子必选结果 7 天只穿一条裤子。" 拆开看是**两个坑叠在一起**，
少修任何一个都还是老样子：

- **下装的重复惩罚原来是按"裤子 + 鞋"的*组合*算的**（`_bottoms`）—— 每天换双鞋，
  这个 key 就变了、罚分归零。于是排出来的是**"上衣天天换、裤子一周不换"**。
  修法：单件也按平方罚（裤子 5.0、鞋 2.5）。
  ⚠️ **两条必须一起改** —— 实测只改裤子，当天就变成"裤子天天换、6 天同一双鞋"，
  只是把"不换的东西"挪了个位置，用户的抱怨原封不动。
- **每个上衣栈只留 3 套变体（`rows[:per_look]`），而这 3 套常常全是"同一条裤子 + 3 双鞋"**
  —— 按分数取，而分数最高的那条裤子总是同一件百搭牛仔裤。**池子里压根没有别的裤子可选**，
  代价函数再对也推不动。修法：组内变体**先按裤子去重**，换裤子的先占位，
  占不满再拿"同裤不同鞋"的补位。

**⑤ 常识下限（`_keep_floor`）。** 试删时不许把清单压到：内搭 < ⌈N/2⌉ 件、
4 天以上只有 1 条裤子、一双鞋都没有、**低于 20℃ 的行程一件能加的外套/衬衫都不带**。
下限会取 min(下限, 清单里本来就有的件数)，所以不会凭空要求一件你没带的东西。

**⑥ 一天用两个温度，别混用。**（2026-09-21 按用户反馈"13-22 度也穿短袖"定的）

| 用途 | 用哪个温度 | 谁决定 |
|---|---|---|
| 打分 / 舒适度 / 好不好看 | `_temp_of`（出门那会儿） | 天气档位：早晚 / 平均 / 午后 |
| 穿几层 / 够不够暖 / 留不留一件能加的 | `_warm_of`（**当天最低温**） | 预报的 `tmin` |

一天 15~21℃，早上出门 15℃、中午 21℃，**用一个温度描述整天必然出错**：
按 21℃ 排就是短袖，早上冻着；按 15℃ 排又会在中午热得脱不掉。
拆开之后两层约束各看各的极端值，谁也不将就谁 ——
而且**不管档位切到哪一档，"18℃ 只穿一件"都不会再出现**。
候选池的枚举温度也跟着用最冷那会儿（`_day_pool(temp=warms[i], score_temp=temps[i])`），
否则外层那个层位根本不存在，再怎么罚也罚不出外套来。

> ⚠️ **试删的可行性判定（`_can_serve`）里，"哪一天本来就排不出来"要跳过。**
> 那个温度缺层位单品时（比如 T 恤上限 30℃ 而气温 31℃），那天跟"带了几件"无关。
> 不跳过的话，试删第一步就被它否掉 —— 实测真实衣橱有一趟旅行因此**一件都省不下来**
> （`dropped_count=0`）。跳过之后同样那趟省下 5 件。
> 容量也只按"能排出来的天"算，别把关卡整个拆掉。
>
> ⚠️ **但"跳过空天"必须拿原始清单当尺子（`base_ok`）。** 只看"这天现在没人穿得了"
> 会把两件事混成一件：**"砍完之后穿不了"** 和 **"衣橱本来就穿不了"**。
> 实测（2026-09-22）：试删把两件卫衣全砍了，而那天早上 12℃（<14℃ 档必需 L2+L3）
> 直接没得穿，却因为"那天是空的"被当成不可抗力放行；紧接着重排填不满 7 天，
> 代码按"宁可多带一件"整体退回原清单 —— 用户看到的是
> **"我明明想少带衣服，你却要我带 7 条裤子"**。

> ⚠️ **可行性判定要用"当天最冷那会儿"（`judge = warms or temps`），不是出门温度。**
> 候选池就是按 `warms` 建的（步①），判定必须同一个口径。
> 实测：用 `temps` 时 15℃ 的下午被当成"不用中间层"，试删把卫衣砍光；
> 而计划里每天都是按 12~15℃ 的早上排的，重排时池子直接空掉。
> **这是同一类错误第四次**（改了一个温度口径、另一处没跟着改），
> 清单见 `rules.item_temp_ok` 那一段。

> ⚠️ **顺序：先修贴身层，再试删（`_repair_l1` 在 `shrink` 之前）。**
> 反过来的话，试删收到的是**一份自身就违规的清单** —— `_greedy` 逐天决策，
> 实测排过"一件 T 恤穿 3 天"（超了 `WEAR_CAP`），而容量闸算的是
> `内搭件数 × 2 ≥ 天数`，这份清单必然不过：**12 次判定全是 False，一件都砍不掉**。
> 贴身层合规的清单才是"这几天排得出来"的见证，试删才有意义。
> （**第 10 次静默失败**：不报错、页面正常，只是"少带件"完全没发生。）

> ⚠️ **原始清单本身就不够轮换时，容量闸要放行（`cap_gate=False`）。**
> 真实数据上就是这个案子：他 7 件 T 恤里有 4 件标了「只能单穿」，
> 12℃ 只剩 3 件能当内搭 → 3×2=6 < 7 天，**这件事本来就做不到**。
> 拿容量当硬闸的代价是裤子鞋子也一件都省不下来 ——
> 现在放行：箱子里照省，内搭由 `_keep_floor` 兜着，
> "某件内搭得重复穿"交给 warns 说实话。**省不了 ≠ 不该省。**

> ⚠️ **候选池不能用今日页那套 `outfits.recommend`。** 它带多样性剪枝
> （「一套要跟已选的每一套至少差 2 件」），那是给今日页「三套互不相似」设计的。
> 放进多天排布里，小衣橱会被它砍到只剩两套候选 —— 实测：8 件衣服时内搭和中间层
> 各只有 1 件可选，「至少差 2 件」就等价于「外层/下装/鞋三个槽位全换」，
> 而三个二元槽位最多只能凑出 2 套。后果是 5 天只排出 3 个不同核心，
> 还会倒过来提示「你衣橱不够」。

> ⚠️ **「少带一件」必须直接问引擎**（`_l1_domain` + `_assign_l1`），不能问候选池。
> 候选池是「挑过的」，用它判断「少带一件还行不行」会系统性低估 ——
> 实测真实衣橱试删出 **0 件**，模型总结还跟着说「有两件只带一件省地方」。

可行性判定分三层（从便宜到贵）：**① 每天都有合法搭配 ② 贴身层总容量够 ⌈N/2⌉ 件
③ 真的排一遍**（回溯：不连穿 + 单件不超上限）。以前判的是"核心互不重复"，
那是按核心算不重样的年代留下的；现在"算不算换了穿搭"看上衣，判定也就落到贴身层上。

> ⚠️ **提示里要提"外套"，先看清单里到底有没有。** 踩过的坑：那几句温差/高温提示
> 原来只按温度区间无条件生成，于是 31℃ 的夏天清单里一件外套都没有，
> 页面却在说"内搭多带一件换洗比多带一件外套有用" —— 用户读到的正是
> **"你说要带外套，穿搭里一件都没有"**。现在凡是要提中间层/外层的句子，
> 都先过 `toppers`（清单里真的存在）这一关，宁可不说。
> 同理 `vision.PLAN_PROMPT` 也明写了：**只许提表里列出的衣服，不许凭常识补一件。**

**⑦ 必带（`must_ids`，旅行页的「必带这几件」）。** 用户手动勾的衣服，三条保证：

1. **能穿就一定排进穿搭** —— `_cost` ⑥ 给含它的候选奖励（只在同一层里比，
   不压过"穿得合不合适"）。
2. **试删一件都不许砍** —— `shrink(protect=...)`。这类件常常正好"只出场一次"，
   按出场次数排序它们排在最前面，不保护就第一个被删。
3. **实在排不进也照样进箱子**，标成「备着」（`wear_count=0` / `must_only`）。

第 3 条是必须的：`_packing` 原来只收"排布里穿过的件"，于是"勾了但没排上"的那件会
**无声消失** —— 用户明明勾了，清单里却没有。什么情况会排不进？
温度不对，或者它被标了「只能单穿」（`solo_only`）而那几天需要叠穿 —— 都正常，照带。

> ⚠️ **候选池的截断要给必带件"保位"，但不许插队（2026-09-22 修）。**
> `max_looks=24` 是按上衣栈截的，而 7 件上衣 × 各自的叠穿组合轻松超过 24 个栈 ——
> 分数低的那个栈整个被挤出去，"必带优先"的奖励就**根本无从下手**（候选都不在池子里）。
> 第一版修法是"命中必带的栈排到最前面"，**这是个灾难**：一条裤子能跟每个上衣栈都搭，
> 于是 24 个栈个个都有"含这条裤子"的变体，**保位变成垄断** ——
> 整个候选池 100% 含那条裤子（实测 72/72 套，24 个栈里 24 个只找得到含它的套），
> 天天只能穿它。用户读到的就是"必带"＝"每天必须穿"。
> 现在改成：**每个必带件只抢一个名额**，剩下的名额一律按分数排。
> ⚠️ 挑哪个名额也有讲究 —— **要挑保暖缺口（gap）最小的那个组**，不能只挑分数最高的：
> 缺口是排序第一关键字，保位保到一个"单层上装"的组，那条裤子会因为"那天不如穿两层"
> 而永远选不上，最后被丢进「备着」（实测：必带裤子明明在池里，7 天一次都没穿上）。
> 改这里也要小心**同分时的 tie-breaker**（用 `look`）：换掉它 = 同分栈的取舍顺序变了 =
> 候选池构成跟着变（实测把秋裤从 10℃ 的排布里挤掉了）。`must` 为空时走的分支
> 与改动前逐字一致，**不许有漂移**。

> ⚠️ **`run()` 的 `busy` 不能"直接丢掉"新请求。** 切到旅行模式那一刻上一轮还在排，
> 用户马上勾一件必带 —— `run()` 被 `busy` 挡掉、静默返回，页面什么都不会变。
> 现在记一笔 `pending`，等这一轮跑完自动补一次。测试里也一样：
> 切模式之后要 `await waitSub`，否则下一步点必带会被丢掉（第一版测试就是这么假通过的）。

## 视觉系统（暖调精品店）

一份 `web/css/app.css` 管 7 个页面 —— **改它 = 全站升级**。所以这里只改样式的**值**，
**从不改类名**：改了类名页面会当场失效，而且不报错（第 11 类静默失败）。

> **上一版走的是"iOS 设置页"**（灰底 + 18px 白圆角卡 + 胶囊按钮 + 毛玻璃 + 蓝/绿/红三个强调色）。
> 用户的判断是「还是觉得展示效果不行，**排版不好配色也不好**」。问题在截图里是看得见的：
> 把「看衣服」的产品做成了**手机 App 的语法**（圆角卡 + 胶囊 + 毛玻璃），观感像后台管理面板；
> 三个强调色同时出现、没有一个主色，眼睛不知道该看哪；
> 控件还是浏览器原生的（`select`/`date`/`range` 四种圆角四种字号），一眼"没做完"。

这是"看衣服"的产品，所以改成**服装画册的语法**（COS / ARKET 那一路）。五条规矩，
都是可指认的项，不是形容词：

| 做法 | 为什么 |
|---|---|
| **纸感底色**：底 `#f4f0ea`（暖米砂），卡 `#fffefc` | 底不是纯白也不是冷灰 —— 整个产品的温度从这里来 |
| **直角 + 细线**：圆角收到 2~4px，1px 暖灰细线，**零阴影** | 精品店的层次是"线和留白"分出来的，不是"光影" |
| **只有一个行动色**：墨黑 `#191714` | 主按钮墨黑实心、次按钮细线描边、删除=陶土红**描边**（不填充）。绿/红/赭黄降级成**只表达结论**（能不能穿）的颜色，不再当按钮底色 |
| **正字距做层级**：中文 `.02em~.10em` | 上一版是负字距收紧（那是苹果大标题的语法）。小标签靠字距拉开，不靠加粗 |
| **衬线只上大标题和数字** | 见下，这是这一版最大的技术风险 |

> ⚠️ **深色模式：已重做并重新上线（2026-09-27 晚）。** 跟着手机系统的
> `prefers-color-scheme: dark` **自动切** —— 用户不用改任何设置。
>
> 旧版被下线是因为**层次没拉开**：底 `#141210`、卡 `#1e1a17`、按钮框 `#423b35`
> 互相只有 **1.10:1 / 1.74:1** —— 等于"卡片没边、按钮没框"，
> 看着就是"一整片黑、分不清哪些能点"。**问题在对比度，不在深色本身。**
> 重做后的四档（都在 `checkmobile.mjs` 里钉着，对着页底 `#1a1917` 算）：
>
> | 元素 | 色值 | 对比度 | 作用 |
> |---|---|---|---|
> | 页面底 | `#1a1917` | — | 暖深褐，不是死黑（纯黑配暖色会发灰） |
> | 卡片 | `#302c28` | **1.27:1** | 从底上浮起来；深色里阴影看不见，只能靠亮度差 |
> | 卡片线 | `#4a443d` | **1.83:1** | 分区靠它 |
> | 按钮/输入框的框 | `#6b6157` | **2.91:1** | **这条才是"看得出哪里能点"的关键** |
> | 三级文字 | `#93887c` | **5.07:1** | 最弱一级也过 AA |
>
> **`color-scheme` 必须写 `light dark`，绝不能写 `only light`** —— 上一轮我写反了。
> 声明"本页拒绝深色"恰恰是**触发浏览器强制暗化接管**的条件：
> Chrome Auto Dark / 安卓 WebView 的 ForceDark / Alook 这类 iOS 浏览器的夜间模式，
> 发现页面不肯适配深色，就自己动手把整页反色压暗，**绕过全部 CSS**
> （实测底栏文字对比度被从 15.6:1 压到 **1.01:1**，字彻底消失 —— 这就是
> "看不到计划/套装"的真相）。**正解是反过来**：页面自己声明支持深色 + 真写一套
> 深色配色 → 这些实现**跳过本页**。于是"深色"从"躲不掉的外来破坏"
> 变成"我们自己控得住的一套设计"。
>
> **剩下的兜底**：如果用户手机上**连纯白都发灰**，那是浏览器的**注入式**夜间模式
> （不走 `color-scheme` 这套标准），页面自身无解 —— 按下面的顺序排查。
>
> **"手机上打开是黑的"排查顺序**
> 1. **先排除"服务在返回旧内容"**：`curl` 服务回来的 HTML/CSS 与磁盘文件
>    **逐字节比对**（`curl .../static/css/app.css?v=NN` 存下来 diff）。
> 2. 让用户报**设置页底部**的「界面版本」（`#uiVer`，从 `app.css?v=` 读、
>    **绝不手写**）—— 旧号 = 他手上是缓存页；新号 = 页面确实是新版。
> 3. 让用户看**设置页的「手机显示自检」**：**纯白**色块 + 生效主题 + 页底实测色。
>    **纯白那块发灰 = 被强制暗化** —— 它写死十六进制，不跟着主题变量走。
> 4. 结论：让他**在浏览器设置里关掉夜间模式**（换手机自带浏览器可立刻验证）。
>    深浅对照图见 `docs/ui-2026-09-27/11-深色模式-深浅对照.png`。
>
> ⚠️ 顺带一条：**对比度是硬指标，不是审美偏好**。三级文字 `--text3` 原本只有
> **3.0:1**（11px 小字要 4.5:1 才达 AA）、按钮边框 `--border2` 只有 **1.5:1**
> （等于"按钮没有边界"）—— 用户的原话是"至少能让我区分这些按钮"。
> 已提到 `#7d7266`（4.6:1）与 `#bcaf9b`（2.2:1），底栏未选中项改用 `--text2`。
> **想调低任何颜色之前，先算一遍对比度。**

配色问题的正解是**减色**而不是换色：从"蓝 + 绿 + 红"三个强调色收到**唯一墨黑**，
其余颜色一律降级为结论色。排版问题则不是审美问题，是六条可指认的缺陷（原生控件、
衣服图是全屏最小的元素、图片不等高、三色打架、文案成灾，加上两个硬 bug：
计划页城市名重复出现两次、今日页副标题被截断）——逐条修掉。

四处最容易踩的坑：

> ⚠️ **顶栏用 grid 两行，不是 flex 一行。** 副标题是"30 件在库 · 能穿出 96 种样子
> （含 1248 种叠穿变体）"这种长句，和 25px 标题挤一行时标题会被压到只剩一个字的宽度 →
> 「今/日」竖排（实测截图抓到的）。堆叠之后标题永远完整，副标题自己 `ellipsis`。
> 这一版没动顶栏布局，规则照旧。

> ⚠️ **衬线字体是本机最大的技术风险。** 本机中文字体只有**宋体**（没有 Noto Serif SC），
> 而宋体的 Latin 很旧。所以 `--serif` 定成 `Georgia, "Songti SC", "Source Han Serif SC",
> SimSun, serif`，并且**只让纯中文大标题和数字碰它**，正文一律无衬线。
> **宋体没有真粗体 —— `font-weight` 必须 400**，给了 600 浏览器就伪粗，整行糊成一团。
> 层级靠字号拉，不靠字重。

> ⚠️ **CSS 变量名一个都不能重命名，只能换值。** JS / HTML 里有内联引用
> （`var(--red)` `var(--text2)` `var(--surface2)` `var(--accent)` `var(--amber)`
> `var(--radius-sm)` …）。改名不会有任何报错，只会有一处颜色悄悄不对。

> ⚠️ **`.card h2` 不能用 `display: flex`。** 设置页和录入页的 h2 里有 `<br>` 和内联
> `<span class="muted">`，一旦变成 flex 容器，`<br>` 就不再换行，那几处标题会挤成一行。
> （h2 现在带 `border-bottom` 细线当分区，**它成为 `.row` 的 flex item 时要 `flex: 1 1 auto`**，
> 否则宽度只有文字那么宽、细线只剩一小截 —— 试穿间「候选件」标题实测就是这样。）

> ⚠️ **原生 `<select>` 的箭头要自己画。** 各平台长相不同、配不上细线语言 →
> `background-image` 内联一份 data URI（12×7 的直角 V）。色值是**写死在 URI 里**的，
> **不跟着 CSS 变量走** —— 所以浅色/深色**必须各写一份**（漏一份 = 深色下箭头看不见），
> 而且改 `--text3` 时这两处得**手动同步**（2026-09-27 就漏过一次：
> 浅色那份还停在旧的 `#9b9186`，而 `--text3` 已经换成 `#7d7266`）。

> ⚠️ **桌面（≥800px）要单独补**，否则 1440px 屏幕上露馅：温度数字离标签隔 400px 空档、
> 底部 6 个 tab 摊满整个宽度、搭配图被拉到 370px 一张。

> ⚠️ **两级确认的按钮必须定宽 —— 按钮宽度决定旁边那段文字会不会重排。**
> 「删」点第一下会换成待确认文案，如果按钮宽度跟着内容走，它旁边的文字列就被挤窄
> （`.info` 是 `flex: 1`），整段介绍当场换行。手机上看到的现象就是
> **「点一下删，左边那行字变形了」**（2026-09-27 用户实拍报的）。
> 实测（390×844）：按钮 46 → **109.5px**，`.info` 152 → **88.5px**，
> 名字 2 → 3 行、meta 3 → 4 行、卡片高 **+101px** —— 按钮抢走的 63.5px
> 恰好等于左边少掉的 63.5px。
> 所以规矩是：**待确认文案只给两个字（「确认」），宽度交给 CSS 硬定宽**
> （`flex: 0 0 46px` + `width/min/max-width: 46px` + `overflow: hidden`，
> 选择器**只认属性**：`.btn.danger[data-del]` / `.btn.danger[data-act="del"]`）。
> 凡是"点了会换文案"的按钮都适用这条。
> ⚠️ 这条**只有 `checkmobile.mjs` 抓得到** —— Python 自检不跑 CSS，
> `checkform` 的 DOM 桩没有排版引擎，宽度变化它根本看不见。
>
> ⚠️⚠️ **两个坑，都栽过**：
> **① 要"定宽"就用 `width`，`min-width` 只是下限** —— 内容比它宽照样撑开。
> 第一版只写了 `min-width: 46px`，结果手机上（HTML 还是旧缓存、文案仍六字）
> 照样撑到 **132px**，用户回「刷新了还是一样的」。
> **② 选择器别绑父元素 class**（`.item-card >` / `.row >`）——
> 多包一层 div、换个容器类名就**静默失效，且不报错**。

**改完必须升资源版本号**（当前 `?v=42`，7 个页面统一）—— 否则浏览器拿的是缓存的旧 CSS，
"改了没变化"。

> ⚠️ **CSS 有 `?v=` 强制换新，HTML 却没有版本号**（只靠 `Cache-Control: no-store`，
> 微信内置浏览器常无视它）→ **两条资源的新旧会不同步**。
> 所以：**任何"改 CSS ＋ 改 HTML 文案"的修复，都不许依赖文案本身**。
> 用户说"没变"时，先看 `serve.out.txt` 里他手机请求的 `?v=`（**有日志就别猜缓存**），
> 再让他报**设置页底部的「界面版本」**（`#uiVer`，从 `app.css?v=` 读、**绝不手写**：
> 手写迟早忘了同步，那就从"自证工具"变成"撒谎工具"）。
> 报旧号 = 他手上是缓存页面；报新号 = 改动真没生效。

### 信息架构：首屏是衣服，不是控制项（2026-09-25）

改版前的今日页**是一台控制台，不是一份答案**：打开第一眼是温度滑杆、天气档位三按钮、
场合下拉，衣服要滚过半屏才出现。实测（390×844，25 件在库）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 搭配卡顶部 | **584px**（占首屏 69%） | **193px** |
| 控制区高度 | 487px（环境卡 355 + 洗衣篮 108） | **84px**（一条温控条） |
| 页面总高 | 3162px（3.7 屏） | **2430px** |
| 横向溢出 / 副标题截断 | 0 / 无 | 0 / 无 |

这不是改方向，是**还原**：`docs/03-V1界面结构.md` 第 54 行写好的首页结构本来就是
「日期 + 天气 + 场合在顶栏、第一眼就是衣服」。实现时漂移成了四张卡。详见 `docs/04-界面改造方案.md`。

三条规矩：

- **整屏只有一个大数字**，就是真正用来挑衣服的那个。改前同屏并排着天气的 `33℃`（33px 衬线）
  和滑杆的 `20℃`（27px 衬线），两个视觉权重几乎相同 —— 用户没法判断"到底按几度给我挑的"。
  现在天气区间和城市降为 12px 次级信息，标签写死一句「按这个温度挑衣服」。
- **温度用步进器，不用滑杆。** 核心组合数是**阶跃**的，实测 16→17℃ 核心组合 32→128（4 倍）、
  20→21℃ 叠穿变体 1056→308（−71%）。390px 宽的滑杆每像素约 0.13℃、手指精度 ±5~8px，
  而且 `input` 只改读数、松手才重算 —— 给不出这个精度。**1℃ 的误差能砍掉七成可用搭配**，
  所以这是数据结论，不是审美偏好。
- **控制默认收起，天气取不到时自动展开。** 档位（按早晚/平均/午后）是一次设好长期不动的偏好，
  不该占首屏、更不该用全站最重的实心墨黑按钮。但 `#panel` 里同时住着**设城市的入口** ——
  天气拉不到时不自动展开，用户就被自己的默认值永久关在无天气状态。这条漏了不报错。

> ⚠️ 改造 `#wx` 时**三处必须同改**（漏一处即点击无反应且不报错）：
> ① 事件委托的容器从 `#wx` 换成 `#panel`；② 天气失败时的城市搜索分支（`wxq`/`wxgo`/`data-city`）
> 一并搬进 `#wxcity`；③ 保留一个 `hidden` 的 `<input id="temp">` 作为**唯一状态源** ——
> 这样 `fetchToday` / `saveEnv` / 「把温度调到 N℃」全部一处都不用改。
> 温控条上的大数字和步进器里的数字**都只是它的读数**。

> ⚠️ **顶栏副标题加了日期，必须复核不被截断。** 它是 `text-overflow: ellipsis`，
> 超了会**静默**截断。实测「9月25日 周五 · 25 件 · 192 种搭配 · 1056 种叠穿」= 宽 250px / 可用 282px，
> `setSub()` 里另有一道兜底：量出来超了就丢掉最后一段（叠穿数），保住前面更重要的信息。

## 图片管线：裁边 → 测色 → 4:5 合成

顺序不能换：**先裁边 → 再测色 → 再合成**（裁边前测色，四角取到的是状态栏，
颜色整个测反）。全部逻辑在 `app/imgs.py`，**只归一化，不做生成式重绘**。

用户实际传进来的是**手机截图**而不是商品原图，所以裁边要同时对付两样东西：

1. **截图外壳**（状态栏、缩略图条、页面留白）—— `strip_bands` 的逐行剖面（`_row_profile`）。
   旧的"背景色簇外接框"法在这里完全失效：背景色在整图里反复出现，外接框 = 整图。
2. **深色模式截图留下的 App 黑背景** —— 2026-09-23 修掉的那个。

### 深色模式黑边：`pad_y` 把 App 背景带了进来

`strip_bands` 找到照片边界后，末尾给裁切框加了 `pad_y`（0.8% 外扩）——
本意是"别让剖面精度把照片的第一行切掉"。但深色模式截图里，那 0.8% 正好是**纯黑的
App 背景**；而 `compose()` 是"等比缩放 + 居中留白"，裁切框的上下边落在画布**内部** ——
于是衣服上下各横着一条黑线。**在用 30 件里 24 件中招**（全部 108 张展示图里 46 张），
这是"展示效果不行"里最刺眼的一处。

修法是 `_shave_dark_edges()`，**两遍**：

1. **200 行剖面粗估** —— 快。但 1350px 高的图上每行大约覆盖 7 个像素，
   边界总差 1~2 行，黑线修不干净。
2. **真实像素行收尾** —— `_flat_dark_run()` 数连续几个"扁平近黑"行（均值 <60 且标准差 <26），
   把粗估剩下的那 1~2 行削掉。**没有这一步就不算修好**：第一版只有第 1 遍，
   实测 24 件 → 3 件；加了第 2 遍才是 **24 件 → 2 件**。

**两道保险**（宁可漏削也不误削，防止把暗底商品照削掉）：整段里暗行占比 >70% 就整体跳过
（那是黑背景拍的鞋、深色大衣）；单侧最多削 5%。

> ⚠️ 改完必须用 `test_crop.py` 里那条断言复核：
> **「深色模式截图：画布内部不许留黑线」** —— 构造一张纯黑底 + 中间贴照片的图，
> 检查裁完之后画布内部没有横贯整条的暗行。**这条断言在只有第一遍实现时当场失败**
> （还剩 2/675 行黑线），加了 `_flat_dark_run` 才过。修完的正确框是 `(48,620,1020,1720)`，
> 正好等于照片范围。

> ⚠️ **重算展示图不要顺手改颜色。** `scripts/renormalize_images.py` 默认会**同时重测主色并写库**，
> 只有加 `--no-color` 才"只重出图、不动颜色"。
> 本轮实测 `--apply` 把 5 件颜色改坏了（米白→浅灰、白→深灰、卡其→浅灰）——
> 颜色不在需求范围内，所以从备份退回了这 5 件原值，再用 `--no-color` 重跑，确认"颜色被改动的: 0"。
> 颜色是本地从像素测的，重跑就可能越界；**要动图就显式声明不动色**。

> ⚠️ **复核黑边用严格阈值**（纯黑 <60、连续 ≥3 行）。用 `thr=110` 这种宽松阈值会把
> 木地板、阴影也算进"暗行"，误报成"3 件贴边"。

## 录入：两层自动

录入这一关是这个项目唯一真正的死亡风险（大多数衣橱 App 的用户录不到 30 件就放弃）。
所以拆成两层，**第二层没配也能用**：

**第一层（零配置，永远可用）—— 每件只点一下。**
照片上传后就地测出主色（本地算法，见下），槽位用手点一下，其余字段按「品类默认值表」
自动填满：正式度、厚度、温度区间、领型、袖型、版型、材质、图案。默认值表在
`app/catalog.py`，34 个品类每个都有一套自洽的值。

**第二层（配了模型，全自动）—— 一下都不用点。**
在录入页右上角「自动识别」里选一个服务商、填 API Key，之后上传即自动填好品类和全部字段，
你只需要扫一眼点「全部入库」。

内置预设：智谱 GLM-4V（有免费额度）、通义千问 VL、硅基流动、月之暗面 Kimi、火山方舟、OpenAI、本地 Ollama。
配置存在本机 `llm.json`（项目根），**会跟着发布上云** —— 所以手机上不用再配一遍。
（它和 `gate.json` 属于同一类：**源码那一半**，跟着每次发布走；
而 `data/` 是**状态那一半**，每台设备各留各的。放错哪一半都不报错，见 `test_config.py`。）

### 一条不肯让的红线：颜色永远本地算

模型只判断**语义**字段（品类/正式度/厚度/温度/领型/材质/版型/图案），
**颜色一律由本地算法从图片像素测出来**（`app/colorlab.py`）。原因：

- 模型的色值随打光变化，同一件衣服两次问可能给两个答案，不可复现
- 颜色直接决定 R4 撞色规则和中性色判定，错一个值会污染之后所有搭配判断
- 本地算零成本、毫秒级、确定性

算法：缩图 → 四角估背景色 → 按颜色距离踢掉背景（等价于一次廉价抠图，不需要 rembg/PyTorch）→
12 位色直方图取最大簇并做邻域平均 → 转 CIELAB 找最近的调色板颜色
（RGB 欧氏距离会把「深灰」和「藏蓝」这种暗色互相抢）。
衣服颜色和背景接近时（白衬衫拍在白底上）自动改用中心区域的空间先验 ——
**绝不退回全图**，那算出来的是背景色，比不判还糟。

模型输出全部过白名单和值域校验（`app/vision.py`），不合法的字段丢掉并记在 `_dropped` 里，
按品类默认值补上 —— 绝不把 `"slot": "上衣"` 这种值写进库。
**任何识别失败都不阻塞录入**：超时、没配 Key、模型胡言乱语，都退回第一层模式。

### 厚度说人话：1–5 只活在接口里（2026-09-28）

用户原话：「关于衣服的厚度或者温度，我其实没有办法判断。能不能简单地用『厚』、『薄』、
『中等』这种比较容易理解的词来写，剩下就交给系统或者大模型来判断，或者用一些比较
直觉性的提示来让大家知道应该是什么样子的厚度」

所以界面上出现的一律是**词 + 一句"像什么"**，1–5 只出现在接口里：

| 值 | 词 | 提示 |
|---|---|---|
| 1 | 很薄 | 像夏天的吊带、雪纺 —— 基本不保暖。 |
| 2 | 薄 | 像普通 T 恤、薄衬衫 —— 单穿刚好，起风就想要件外套。 |
| 3 | 中等 | 像针织衫、厚衬衫 —— 有点像秋装。 |
| 4 | 厚 | 像卫衣、皮衣、厚针织 —— 秋天单穿，或冬天当内层。 |
| 5 | 很厚 | 像羽绒服、厚大衣 —— 一看就很鼓。 |

- **词表只有一份**，在 `web/js/api.js`（`THICK_WORDS` / `THICK_HINTS` / `thickPicker()`）。
  待入库卡、已入库「改字段」面板、试衣间三处共用。抄第二份必然漂移，
  最后就是"录入页说厚、试衣间说很厚"。**`checkthick.mjs` 会扫全仓库把这个钉住。**
- **那个 `<input type="range">` 仍然在场，但是藏起来的** —— 它才是唯一的状态源，
  5 个词按钮只是它的**遥控器**（写 `value` + 派发事件），跟今日页那个 hidden `#temp` 是同一招。
  **藏起来是刻意的：一个没有刻度的滑杆等于什么都没给。**
- ⚠️⚠️ **遥控器必须同时派发 `input` **和** `change`，少一个就是静默失败：**
  `input` 是待入库卡（`#grid` 的 `onField`）和试衣间（`#form`）拿新值的路子；
  **`change` 才是已入库「改字段」面板落库的路子**（`#list` 的 `change` → `patchField`）。
  只派发 `input` 时：词点下去**界面变、数据库不变**——页面一切正常、不报错、刷新就退回去。
  这一条**只有在真浏览器里点一下、再去接口读一次**才看得见。
- 词按钮 `flex: 1 1 **0**`（不是 `auto`）。`auto` 是**假的等宽**：basis 取内容宽度，
  实测 `[90,78,90,78,90]` —— "薄"比"很薄"窄 12px。改成 `0` 之后 `[85,85,85,85,85]`。
- 自检：`scripts/checkthick.mjs`（**真开浏览器 + 真落库 + 收尾精确还原**，A–J 不变量，本轮另加 F2、F3 两节）。
  ⚠️ **F3 是"用户手选的值不许被识别结果冲掉"**：识别要跑好几秒，这几秒里用户自然已经在纠错了；
  不加保护的话，模型一返回就 `Object.assign` 把他改的整片盖回默认值 ——
  界面上就是"选了之后又跳回默认选项"。**这条打桩复现**（真调模型要联网要等，"谁先谁后"没法稳定复现）。
  两个录入入口都要挡：`prebuy.html` 用 `_touched` 合进 `keep`，`wardrobe.html` 在 `Object.assign` 前后快照/盖回。

## 启动

| 双击 | 效果 |
|---|---|
| `start.bat` | 只有本机能访问 `http://127.0.0.1:8077`（最安全，日常用这个） |
| `start-lan.bat` | 额外监听局域网，手机同 WiFi 可访问。横幅会印出**真实网卡地址**（不是代理的 fake-ip，见下） |
| `start-remote.bat` | **让手机在任何网络都能打开**（不只在同一个 WiFi）—— 第一次跑会把 Tailscale 装/配好 |
| `phone-url.bat` | 打印该打开的地址 + 生成二维码图（`docs/phone-qr-*.png`）。**IP 变了就双击这个** |

`phone-url.bat` 的逻辑在 `scripts/phone_qr.py`，它做三件事：算出地址 → **先探一次确认真的连得上**
→ 生成二维码并**自己解码回读一遍**（读出来的必须正好是那个网址，否则明确报错，不给你一张扫不出的图）。
IP 是路由器动态分配的，换网络、重启路由器就会变 —— 所以别记地址，记这个脚本。
配好远程之后它会出**两张**卡片（局域网 + 远程）；`--lan` / `--remote` 可以只要一张。

命令行带参数也行：`start.bat --lan --port 9000`。

**注意：`start.bat` / `start-lan.bat` 必须保持纯 ASCII，不能往里加中文。**
cmd.exe 按系统代码页逐行解析 `.bat`，文件里出现多字节字符（中文）再叠加 `chcp`
切代码页，cmd 会丢失文件读取位置，把后面的行读成碎片，屏幕上就是一堆
`'xxx' 不是内部或外部命令` + `系统找不到指定的路径`。所有中文提示都放在
`scripts/serve.py` 里，由 Python 打印。

手动启动（等价于 `start.bat`）：

```powershell
# 本机
python scripts/serve.py
# 局域网
python scripts/serve.py --lan
```

### 端口 8077 被占了怎么办

启动器自己会处理，不会甩 traceback：

- **占端口的就是本应用**（最常见：你已经启动过一次，窗口还开着）→ 直接告诉你「服务已经在运行了」和地址，不当成错误
- **被别的程序占了** → 自动往后找空闲端口（8078、8079……）并说明换了哪个
- 想指定端口：`start.bat --port 9000`

早期版本这里会甩一段 `[Errno 10048] WinError 10048` 的英文错误，看不出该怎么办 —— 已修。

### 手机打不开的排查顺序

0. **先看横幅印的地址是不是 `198.18.x.x` 那种。** 装了 Clash / Surge 一类的代理
   （fake-ip 模式）就会踩这个：代理建一块虚拟网卡并**抢走默认路由**，于是
   "连个不可达地址看本机 IP" 那招返回的是 `198.18.0.1` —— 局域网里根本没这台机器，
   手机只会一直转圈。`serve.py` 现在**枚举网卡地址，再过滤掉回环 / 链路本地 /
   198.18 / 198.19**，横幅只印真实网卡那个，并把它当"连不上换这个"的备选列在后面。
   自检见 `scripts/test_lan.py`（离线，41 条断言）。
1. 确认用的是 `start-lan.bat`，且 Windows 防火墙弹窗里点了「允许访问」（Python 第一次监听外部地址时一定会弹）。
2. 确认手机和电脑在同一个 WiFi（不能一个连 5G 一个连 2.4G 的不同网段，也不能手机开着流量）。
3. 局域网 IP 会变（重启路由器后）。**双击 `phone-url.bat`** —— 它重算地址、验一次能不能通，
   再把二维码图打开给你扫，不用自己去查 IP。服务没开 LAN 模式时它会直接说「先双击 `start-lan.bat`」，
   不会给你一张扫出来打不开的二维码。
4. 都不行就在手机浏览器里试 `http://<IP>:8077/api/meta`，能出 JSON 说明网络通、是页面问题；出不来是网络问题。
5. **出门在外（不在同一个 WiFi）**：双击 `start-remote.bat` —— 见下面《出门在外：远程访问》。
6. 零安装的兜底：**手机开热点让电脑连**，这样又回到同一个网段（代价是电脑得在身边）。

### 出门在外：远程访问（2026-09-29）

局域网那套（`start-lan.bat`）只在**手机和电脑连同一个 WiFi** 时成立。
出门在外要用，双击 **`start-remote.bat`**：它把三道门依次走一遍，缺一道手机都打不开。

| 门 | 做什么 | 谁做 |
|---|---|---|
| ① 装 | 电脑和手机各装一个 Tailscale | 你（电脑双击 `tools/tailscale-setup.exe`；手机去应用商店装） |
| ② 登录 | 两边加入同一张私有网 | 你（脚本会打印一个 `login.tailscale.com/...` 网址，用浏览器登录；手机登**同一个账号**） |
| ③ 反代 | `tailscale serve` → `https://<机器名>.<tailnet>.ts.net` | 脚本自动（第一次可能要你去后台开一下 HTTPS Certificates，它会告诉你点哪） |

**为什么用 Tailscale**：它给的是**私有网** —— 只有你自己登录的设备能连，不是"谁拿到网址谁能进"。
流量端到端加密直连，衣橱数据和衣服照片**不出这台电脑**。免费（个人用足够）。

**为什么是 `serve` 不是 `funnel`**：

| 命令 | 谁能访问 | |
|---|---|---|
| `tailscale serve` | 只有你 tailnet 里的设备 | ✅ 用这个 |
| `tailscale funnel` | **整个公网** | ❌ 绝对不要 |

两者只差一个词。本应用**零鉴权**（全仓只有一处 `api_key`，那是 DeepSeek 的密钥、
不是登录密码），`funnel` 出去 = 谁拿到网址谁就能看你衣橱、删你衣服。
同一个理由：**不要用 ngrok / Cloudflare Tunnel 直接把端口捅到公网** —— 真要暴露，先加一道口令。

**✅ 顺带解决"装不成 App"**：`serve` 给的是 **https**，而 https 是浏览器的"安全上下文"——
安卓 Chrome 才肯真把它装成 App。局域网那种 `http://192.168.x.x:8077` 不行
（顶多给个快捷方式，没有 Service Worker，也就没有离线能力）。

**代码落点**（三处共用一份判定，不写第二套）：

- `serve.py`：`_is_tailnet()` / `tailnet_ips()` / `tailscale_info()` / `remote_url_from()`。
  横幅多印一行「远程访问」；没装时印「未开通 + 双击哪个文件」，**一个地址都不编**。
- ⚠️ **`lan_ips()` 必须排掉 tailnet 段（100.64.0.0/10）。** 它的语义是"任何网络"，
  而 `lan_ips` 的语义是"手机连同一个 WiFi" —— 混成一栏，用户出门会以为还得先连上同一个 WiFi。
  **分组 ≠ 过滤**：tailnet 地址照样是能连的地址（`_unreachable` 放行），只是要分开放。
- `setup_remote.py` = `start-remote.bat` 的真身；`phone_qr.py` 配好后出第二张卡片。
- 自检 `test_lan.py` 第 ⑤ 节（⚠️ `tailscale_info` 一律**打桩** —— 真实环境里装没装它会变，
  拿它当断言依据就是让断言依赖跑测机器，这个项目栽过，见第 ② 节的注释）。

**两条诚实的边界**：

- **本机访问自己的 tailnet 地址未必通**（hairpin 不一定支持）。所以 `phone_qr.py`
  探不到时**不说"手机也不行"**，只报事实、让用户拿手机试 —— **给错结论比不给结论更糟**。
- **电脑必须开着**（手机只是显示器，衣服和照片都在本机）。本机电源方案是
  **高性能、插电时永不睡眠**，所以不会自己断；但**重启之后服务要重新起**
  （除非设了开机自启）。

### 手机端适配：六条硬指标（2026-09-27）

用户是**在手机上用**这个工作台的，所以下面这些不是"优化"，是底线。
全部由 `scripts/checkmobile.mjs` 自动检查（无头浏览器 + CDP，量的是真实排版）。

| 指标 | 钉成 | 为什么 |
|---|---|---|
| 可点元素 | **≥ 36×36px** | Apple 建议 44、Material 48；这个语言里次级按钮是细线小牌，38 是"看得清编排"和"点得中"的平衡点。实测改前：「洗了」**24×20**、标签 27 高、次级按钮 32 高 —— 手指点不中，功能等于不存在 |
| 底部导航文字 | **≥ 11px** | 改前 9.5px，是"App 的导航"不是脚注，手机上读不清 |
| 横向溢出 | **0** | ⚠️ 横滑条（`.pstrip`）里的元素天然超宽，**那是设计不是 bug** —— 检查脚本会排除可滚动容器内部的元素 |
| 深色下的**层次** | 卡/底 **≥1.20:1** · 框/底 **≥2.50:1** · 底栏文字 **≥4.00:1** | 深色跟着系统**自动切**（不用手动改设置）。只验"够不够黑"没用 —— 旧版也黑得很"正常"，问题是**卡片和底一个色、按钮框看不见**（见「视觉系统」那节） |
| 顶部安全区 | `env(safe-area-inset-top)` | 加到主屏幕后是 standalone、没有地址栏，iPhone 的刘海会直接压在大标题上。**底部很早就处理了，顶部一直漏着** |
| 输入框字号 | 触屏设备 **16px** | iOS Safari 的硬规则：`font-size < 16px` 的输入框**一聚焦就把整页放大**（"点一下输入框，页面突然变大"）。用 `@media (hover:none) and (pointer:coarse)` 精准命中手机/平板，鼠标设备不受影响 |
| 点了会换文案的按钮 | **硬定宽** | 两级确认的「删」点一下会换成待确认文案，按钮跟着内容一宽，旁边那段介绍就被挤到换行。旧写法实测：按钮 **132px**、`.info` 152 → **66**、名字 **2 → 4 行**（360 视口下更狠：info → **36**、名字 → **6 行**）。规矩见上面那条 ⚠️：**文案只给两个字 ＋ CSS 用 `width` 硬定宽**（`min-width` 不够，它只是下限） |
| 行内文字链接 | **热区 ≥ 36px** | prebuy 空态里「手动填一件」是那个页面**唯一**的录入兜底入口，原来只有 **63×17px**，手指点不中。修成 **79×44**：用**负 margin 抵掉 padding**，视觉一动不动、只有热区变大。⚠️ 它在通用扫描里**假绿过** —— 取几何时还没渲染完、rect 是 0×0，被当成"不可见"跳过了 → 已补**点名测量**的专项 |

### 录入页为什么是「一行一件」（2026-09-27）

录入成本是这个项目**唯一真正的死亡风险**，所以这一页的密度是硬指标。
实测（390×844，无头浏览器量的真实几何）：

| | 改前 | 改后 |
|---|---|---|
| 待入库 · 单件 | **358.6px** × 26 件 = 9596px | **166px** |
| 已入库 · 单行 | **241.3px** × 27 件 = 5521px | **76px** |
| 点「改字段」 | 那一行 241 → **1065px**，面板挤在 `.info` 栏里只有 **152px 宽 / 814px 高** | 掀一张 **362px** 宽的覆盖面板 |
| 整页高度 | **15945px**（≈19 屏） | 7664px |

- 待入库「同一段颜色警告从 26 张卡收成列表顶一条」：实测 13 条内容**完全一样**。
  只提**出现 ≥2 次**的那几句（出现一次的仍留在那一行里，不丢信息）。
- 已入库「改字段」从"在列表里展开 17 个控件"改成**掀一张只盖这一件的面板**。
  「删」也搬进面板 —— 列表行里只剩「改字段」，所以 `checkmobile` 那两节删除断言
  **必须先揭开面板**，否则 `querySelector('[data-del]')` 是 null、会**静默跳过**（假绿）。
- ⚠️ **只动容器与布局**：字段、`_picked` 校验、`toPayload`、`PATCH` 逻辑一行不改。
- ⚠️ 面板上挂 `item-card` 类**只是为了**让 `patchField` 里那句 `el.closest('.item-card')`
  原样命中 —— 差这一个类就**改了不落库、且不报错**（`checkform` 已钉死这条）。
  所以覆盖样式必须写在 `.item-card.item-sheet`（**两个类**）上：单类 `.item-card`
  是盖不掉 `.item-card { display:flex; padding:12px }` 的。
- ⚠️ 面板必须画在 `#list` **里面** —— 这一页所有交互委托在 `#list` 上，
  挪到 `body` 就会**点了没反应**。
- ⚠️ 待入库那 7 个槽位按钮 **`flex-wrap: nowrap`**：wrap 时「配饰」会单独掉第二行
  并占满整行，单卡从 162px 涨到 **202px**（+25%）。现在空间够就平分、
  真不够（窄屏）横向可滑（`overflow-x:auto`，会被 `checkmobile` 的溢出扫描自动豁免）。

⚠️ **改完 CSS 一定要跑 `checkmobile.mjs`。** 这类问题不会报错、不会进日志，
只有真机上手才知道点不中。这个项目已经吃过两次：
把标签的 `padding` 从 11 加到 13（横向只多 6px），录入页那两个标签就**悄悄掉到第二行**
—— 因为卡片右栏只有 155px，`68+68+6=142` 放得下，`76+76+6=158` 就换行；
2026-09-27 又一例：录入页点一下「删」，左边的介绍文字当场重排。
**Python 自检不跑 CSS，`checkform` 的 DOM 桩没有排版引擎，都看不见这种事。**

### 装到手机上：局域网 → PWA → APK / 鸿蒙（2026-09-27）

三层，成本差一个数量级。**先只做第一层**，绝大多数需求到那儿就够了。

**第 1 层 · 局域网（已就绪，零配置）**

`start-lan.bat` → 手机连同一个 WiFi → **双击 `phone-url.bat`**，扫它生成的二维码即可
（它会先探一次可达性，再把地址和二维码一起给你；服务没开 LAN 模式时直接告诉你先跑 `start-lan.bat`）。
电脑必须开着，因为**服务和数据都在电脑上**（`data/closet.db` + `data/images/`）——
手机只是个显示器，**不能离线用**。

**不在同一个 WiFi 怎么办？** 先把两件事分开：「出门也能用」≠「挂到公网」。

- **Tailscale（推荐）**：把电脑和手机拉进**同一个私有网**（不是公网，别人看不见）。
  手机在任何网络下（4G / 别的 WiFi）访问 `http://100.x.x.x:8077`。
  数据不出本机，**不用改一行代码**。安装包在 `tools/tailscale-setup.exe`。
- **手机开热点让电脑连**：零安装的兜底，代价是电脑得在身边。
- ⚠️ **别用 ngrok / Cloudflare Tunnel 裸暴露** —— 见本节末的鉴权警告。

**第 2 层 · 添加到主屏幕（PWA，已就绪）**

7 个页面都挂了 `manifest.webmanifest` + 四个尺寸的图标（`scripts/make_icons.py` 生成，
改完图标记得重跑）。手机上打开地址 → 浏览器菜单 →「添加到主屏幕」/「安装应用」。

| 手机 | 结果 |
|---|---|
| iPhone / Safari | ✅ 认 `apple-mobile-web-app-capable`，以**独立窗口**打开，没有地址栏 |
| 安卓 / Chrome | ⚠️ **多半只是个快捷方式**，点开还是带地址栏的浏览器 |

安卓为什么打折：`http://` 不是**安全上下文**，Service Worker 注册不了，
Chrome 于是不认它是个"可安装的 PWA"。**要真安装，得先给它一个 HTTPS 地址。**

**第 3 层 · 真·独立 App**

| 路子 | 需要什么 | 备注 |
|---|---|---|
| **Tailscale + 开 HTTPS 证书**（推荐） | 在 Tailscale 后台点一下 "HTTPS Certificates" | 之后可用 `https://<机器名>.<你的tailnet>.ts.net:8077` —— **是安全上下文，PWA 立刻可安装**；而且它**仍然是私有网**（只有你自己登录的设备能连），比 Tailscale **Funnel**（那个是发布给全世界的公网）安全得多 |
| 其它 HTTPS 地址（Cloudflare Tunnel / Tailscale Funnel / 发布到云） | 一个隧道或一台服务器 | 能同样解决"可安装 + 出门可用"，但**都是公网**，务必先看下面的鉴权警告 |
| 包成 APK（TWA / Bubblewrap、Capacitor、WebView 壳） | JDK + Android SDK + Gradle（数 GB），或丢给 GitHub Actions 云端构建 | 本机**一样都没有**（2026-09-27 实测）。壳里装的仍然是那个网址 |
| 鸿蒙 | DevEco Studio + 华为开发者账号 + 签名证书 | **HarmonyOS NEXT 不再兼容 APK**，得用 ArkTS + `Web` 组件重写壳；HarmonyOS 4 及以下（Android 内核）仍能装 APK |

⚠️ **挂公网之前必须先加一道门。** 这个应用**没有任何鉴权**（`api_key` 只是大模型配置，
不是访问控制），谁拿到地址谁就能看、改、删你的衣服。**这道门现在已经有了**
（`app/gate.py`，见《发到云上》），而且 `stage_deploy.py` 会在没有口令时**拒绝发布** ——
所以别再手工裸暴露，走那条路。

### 数据完整性：两条不许破的规矩

1. **删单品只能走 `db.delete_item()`**，不许裸写 `DELETE FROM items`。
   `outfit_items.item_id` 如果没有 `ON DELETE CASCADE`，配上 `PRAGMA foreign_keys = ON`
   会直接撞外键 —— 前端表现是"点了删除什么也没发生"（已踩过）。
   老库会在服务启动时自动自愈（清孤儿 + 重建外键，先备份）。
2. **不许裸 `sqlite3.connect()`**。它默认 `PRAGMA foreign_keys = OFF`，
   级联不触发会一行行攒出孤儿记录。只许用 `db.get_conn()`。
   `PRAGMA foreign_keys` **在事务里是空操作**，改它之前必须先 `commit()`。

`scripts/apitest.py` 收尾是**快照 → 还原**，不是清空表 —— 别退回到 `DELETE FROM outfits`。

## 算法要点

**六个核心字段决定能不能搭**：品类槽位、主色 + 是否中性、正式度 1–5、温度区间、厚度等级 1–5、领型。加上衣长、袖型、版型三个补充字段供叠穿规则用。

**温度决定「必需层 / 可选层 / 叠层上限」，不是一个固定层列表**（`graph.layer_plan`）：

| 温度 | 必需 | 可选 | 叠层上限 |
|---|---|---|---|
| ≥24℃ | 内搭 · 下装 · 鞋 | — | 1 |
| 18–23℃ | 内搭 · 下装 · 鞋 | 中间层 · 外层 | 2 |
| 14–17℃ | 内搭 · 下装 · 鞋 | 中间层 · 外层 | 3 |
| <14℃ | 内搭 · 中间层 · 外层 · 下装 · 鞋 | **内穿下装** | 3 |

中间层和外层**可选**，所以「今天不穿外套」是一个合法搭配（23℃ 穿 T恤+裤子+鞋是正常的）。
反过来，必需层缺合格单品时该分支**直接作废**，不会推出「0℃ 没穿外套」的方案。
叠层上限是新的物理约束：20℃ 不该出现三件叠穿。

### 内穿下装（L4I）：秋裤终于有地方放了

用户原话：「秋裤按 L4 录进来，30℃ 那天被排出来了。」
根子不在数据 —— **是只有 L1–L5 五个槽位，没有"裤子里再穿一件"这个概念**。
2026-09-21 加了 `L4I`（内穿下装 / 秋裤 / 打底裤），它有三条不许破的性质：

1. **只在 14℃ 以下进候选**（`layer_plan`）。14℃ 以上一次都不出现 ——
   于是"30℃ 排出一条秋裤"从根上不可能，**不用去改那件标着 -5~34℃ 的数据**。
   它永远是「可选」：0℃ 不穿秋裤也是合法搭配。
2. **加不加它，核心组合数一个都不变。** 核心 = 最外层上装×下装×鞋，
   秋裤被外裤盖住，不改变"穿出门看起来是什么样"。这条破了，
   衣橱体检的密度、买前模拟的 ΔN 会全部失真。
3. **它永远被外裤盖住**，不单独出现；颜色与正式度也**不参与判定**
   （`rules.HIDDEN_SLOTS`）—— 秋裤是高饱和色也不该跟别人"撞色"，
   拿它衡量"今天够不够正式"更是没道理。

温度口径跟内搭同理（`COVERED_SLOTS`）：**只校验上限**，冷不该由它负责。
自检见 `scripts/test_l4i.py`（离线，跑真实衣橱 + 一件内存里的假秋裤）。

> ⚠️ 加这个槽位要动 `items` 表的 `slot` CHECK 约束，而 **SQLite 改不了约束** ——
> `db._rebuild_items()` 会建新表→搬数据→换名（自动跑，先备份）。
> 建表语句从 `schema.sql` 里抓、列清单从 `PRAGMA table_info` 现取，
> 就是为了不留一份会和 schema 漂移的手写列清单（漂移的下场是**悄悄少搬一列**）。

**温度适用性分暴露层和被覆盖层，不按同一个口径解释**（`rules.item_temp_ok`）：
视觉模型给的温度区间是「这件**单穿**舒不舒服」。

- **暴露层（外层/下装/鞋）**：上下限都要满足
- **内搭 / 内穿下装**：**只校验上限** —— 它们永远被盖住，冷不该由它们负责。
  长袖 T 恤标 15~30℃ 说的是单穿，8℃ 穿「T恤 + 卫衣 + 夹克」完全正常
- **中间层**：外面还有外层时只校验上限，没有外层时双边

上限永远有意义（30℃ 不该穿厚内搭、0℃ 不该穿薄外套）。

**R2 也必须按"有效区间"判，不能拿原始区间比。** 长袖 T 恤（15~30℃）和羽绒服（-10~10℃）
原始区间不相交，但「T恤 + 卫衣 + 羽绒服」正是冬天最正常的穿法。按原始区间判的实测后果是
**一件羽绒服一件衣服都搭不上**（参与次数 0）。现在内搭/中间层按被覆盖算、下限放开，
真正需要防的是「夏天短裤 + 冬天长靴」这种**都暴露在外**的错配，那个仍然拦得住。

**硬规则**：
- R1 同槽位不搭 · R2 温度区间必须相交 · R3 正式度差 ≤ 2 · R4 两个高饱和色不搭 · R5 中性色无限兼容
- D1 厚度单调（内薄外厚）· D2 领型兼容 · D3 长度关系 · D5 正式度单调 · D6 袖型

**温度过滤必须在候选生成阶段做，不能只在最后校验。** 只在叶子上判的话，
DFS 会把「最高 20℃ 的外套」排进 23℃ 的每条路径、**每条都被叶子否掉** ——
结果不是「少几套」而是直接 0 套、首页空白。提前筛还有个白拿的好处：搜索空间小一大截。

**算不出搭配时要能自证**（`Closet.diagnose`）：说清哪一层、这一层里能穿的有几件、
库里总共有几件，再给一个「最近的可用温度」按钮。
以前只说「多半是某一层缺件」，等于把问题丢回给用户。

**枚举不落全量列表**：DFS 逐层剪枝，用回调计数。28 件衣橱跑 5 个温度带不到 50 毫秒。
核心组合枚举结果带进程内缓存（缓存键含集合指纹，改单品属性自动失效），重复请求 0.01 毫秒。

## 主指标：核心组合，不是"合法搭配数"

**核心 = 最外层上装 × 下装 × 鞋。** 叠穿多出来的层算同一个核心的变体。

```
T恤 + 皮衣 + 裤 + 鞋
T恤 + 卫衣 + 皮衣 + 裤 + 鞋   →  同一个核心（穿出门是同一个样子）
T恤 + 裤 + 鞋                  →  另一个核心（不穿外套，看起来确实不一样）
```

为什么必须这样数：层数可变之后路径数是**乘法**膨胀的。同一件衣橱 20℃ 能跑出 2240 条合法路径，
但折成核心只有 **512 个** —— 前者不回答"最少几件衣服能搭出几种样子"，后者才回答。

| 指标 | 算法 | 怎么用 |
|---|---|---|
| **核心组合数** | 去重后的 (上装, 下装, 鞋) 个数 | 主指标。"能穿出几种样子" |
| **组合密度** | 核心组合数 ÷ 理论上限 | **尺度无关**，0–100%。衣服越多它不会自动变大 |
| 叠穿变体 | 合法路径总数 | 参考：同一批核心有多少种穿法 |
| 平均套/件 | 核心组合数 ÷ 在库件数 | 只看同一件衣橱随时间的趋势 |

**组合密度才是能横向比的数。** 100% = 你现有的衣服两两都搭得上，没有互相打架的；
掉下来就说明有一部分衣服跟别的配不起来。理论上限 = 合格上装数 × 合格下装数 × 合格鞋数，
其中"合格上装"由层次结构决定 —— 冬天外层是必需的，顶层就只能是外套，
内搭再多也不产生新核心。

ΔN（买前模拟）、救活数、枢纽件排行的单位也都是**核心组合**。

**候选件是影子单品**（`stage='candidate'`），绝不参与衣橱效率 / CPW / 孤岛枢纽 / 推荐。所有统计一律只跑 `stage='owned' AND status='in_wardrobe'`。

## 三个容易被忽略的判断

**ΔN 单独用会骗人（空洞效应）**：你衣橱里没有大衣，那么任何一件大衣录进来 ΔN 都会很大 —— 那不是这件大衣的功劳，是你的衣橱有个洞。检测到该槽位为空时，系统会改成说「你缺的是这个位置，不是这一件」，并建议横向对比同品类候选。

**ΔN 只在单一温度上算**：跨季节累加会让数字虚高到几百套，对决策毫无意义。「覆盖几个季节」是另一个指标。

**决策门槛用相对增长率，不用绝对套数**：衣橱越大，同样的衣服绝对增量越大，绝对阈值会失效。

## 发到云上（手机随时能打开）

用「发布为应用」把整个项目发成一个网址 —— **手机、平板、电脑打开的是同一个网址、同一份数据**，
出不出门、在不在同一个 WiFi 都无所谓。本机那三种启动方式（`start.bat` / `start-lan.bat` /
`start-remote.bat`）原样保留，互不影响。发布后你会拿到一个自己的网址 ——
**这个仓库里不写具体地址**，那是每台机器各自的事（`CLOSET_URL` 环境变量，
或直接改 `scripts/checklive.py` / `pull_cloud.py` / `cloud_qr.py` 顶部那个占位符）。

### 三条要记住的

**① 上云必须带口令。** 挂到公网之后**谁拿到网址谁能进**。所以项目根有 `gate.json` ——
**文件在，门就启用**：非本机访问要口令，本机不用（`start*.bat` 走 `serve.py`，它显式 `CLOSET_GATE=off`）。
生成/更换口令：`scripts/set_gate_password.py`（`--show` 看当前）。
⚠️ 口令文件读坏时必须**关死**（不是敞开）—— `test_gate.py` 有一条专门盯这个。

**② 云上启动命令不能写 `--port $PORT`。** 发布侧的启动命令**不经 shell 展开**，`$PORT` 会变成空串 →
uvicorn 抛 `Option '--port' requires an argument` → 服务起不来，界面报"60 秒内不可达"，
看起来像端口冲突，其实是展开问题。**踩过一次。** 正解：`python scripts/serve_cloud.py`
（在 Python 里读 `PORT`，读不到回落 3000）。

**③ 云上是"投影"，不是第二份数据 —— 但可以做到不顶掉它。** 关键只有一个开关：
**发布带不带本机 `data/`**。2026-09-30 实测两轮：

| 发布方式 | 云上那份 | 实测 |
| --- | --- | --- |
| 带 `data/` | **被本机顶掉** | 云上把 `comfort` 改成 21.5 → 重新发布 → 退回本机的 19.0 |
| **不带 `data/`** | **完整保留** | 标记值 23.5 与 27 件都活着；手机上改的东西留得住 |

**所以 `stage_deploy.py stage` 的默认行为就是不带 `data/`** —— 手机改的留得住，
靠的就是这一行，不需要账号、不需要云数据库。

> ⚠️ 于是有一个必须自己记住的分工：**云上那份是"活的"，本机那份是"原件"**。
> 两边都会各自往前走。想合流，用 `scripts/pull_cloud.py` 把云上的拉回本地
> （默认只下载到 `backups/`，加 `--unpack` 才会覆盖本机 `data/`，且**先留档**）。
> `--with-data` 只在一种场合用：**云上那份丢了，拿本机备份推回去** —— 它会覆盖云上的一切。

### 一个人用，两份设备怎么不分家

这是"单人自用"这个前提下最省事的做法，不需要任何账号系统：

- **电脑是主编辑处**：加衣服、改字段、点反馈，都在电脑上干。
- **手机是随身读 + 随手改**：打开同一个网址，加一件、记一笔都写进云上那份。
- **两边靠"发布不带 data"不下架**：电脑上重新发布**不会**回滚手机上的改动。
- **定期拉一份回来**：`python scripts/pull_cloud.py`（只下载，不动本机）。想在本机看到
  云上那份的最新样子，再 `--unpack`（会把现役 `data/` 改名留档，不直接毁掉）。
- **兜底**：云上 `GET /api/backup` 可以直接下整包 zip（要过口令），
  或者干脆 `pull_cloud.py`。

```bash
python scripts/make_source_zip.py --list-only  # 只报告要打什么、扫出什么，不落盘
```

它做的四件事，每一件都是"不问就会出事"的那种：

1. **排除你自己的东西**：`data/`（整柜衣服和照片）、`gate.json`（**口令**）、
   `llm.json`（**模型 Key**）、`.workbuddy/`、`tools/`、旧备份、自检输出、发布产物。
   ⚠️ 后两个都在**项目根** —— 而项目根正是"该跟着发布上云"的那一半，
   所以**绝不能靠"白名单里没写它"来兜底**（某次手滑加个通配符就静默失效了）：
   要显式列进 `SECRET_FILES`，打完包再**按名字点名复验**一遍。
2. **打之前扫口令和密钥**：命中就**中止、一个字节都不写**。扫描规则先跑一遍
   **正反样本自检** —— 一个永远说"没发现"的扫描器和真扫描器长得一模一样。
3. **个人痕迹只报告**：你自己的线上网址、本机用户名、项目绝对路径。这类东西别人拿去
   跑不起来，但拦下来会很烦，所以只说、不拦。
4. **打完回读复扫一遍**：防"扫的和打的不是同一批"。

包里带一份 `RUN-FIRST.md`，是给**拿到源码的人**看的（怎么装、怎么跑、怎么发到自己的云上），
和本文（为什么这么设计）分工不同。

> ⚠️ 打包前如果 `data/` 正被 `stage_deploy.py` 挪着，脚本读不到你的 Key，
> 「没发现密钥」就是一句空话 —— 它会**明说**这件事，不装绿。

### 每次发布前后各跑一条

```bash
python scripts/stage_deploy.py stage      # 挪走 data/（**默认**）+ 旧备份/安装包
#   ⚠️ 模型配置 llm.json **刻意不搬** —— 它就该跟着上云，手机那份才不用重配
#   ⚠️ 没有 gate.json 会直接拒绝发布 —— 那是有意的（本机免密，只有这一步拦得住）
# …发布…
python scripts/checklive.py              # 门挡得住吗 / 数据在吗 / 写得进吗（打完把 comfort 还原回去）
python scripts/stage_deploy.py restore    # 原样搬回
```

`checklive.py` **打的是线上、不打本机**，所以**不算进那 25 项**（那 25 项要能离线/本机跑）。
重新发布之后想确认"云上那份变成什么样了"，用 `python scripts/checklive.py --recheck`。

- **密钥上云（2026-10-01 反转的）**：`llm.json` 里的 `api_key` **会**跟着发布传上去。
  原来写的是"密钥不该上云"，于是它被挡在门外 —— 代价是**云上那份永远没 Key**，
  手机上的录入页就催你在手机上重配一次**电脑上早就配好**的东西（用户报的"逻辑不统一"）。
  反转的理由：`gate.json`（**进门口令**，拿到就能进你的衣柜）一直就是跟着上云的，
  它比模型 Key 敏感得多 —— 把两者区别对待站不住脚。
  真要挡住的话，该挡的是**分享包**，而那一侧 `make_source_zip.py` 已经挡住了。
  上云后识别**优雅降级**（说"未配置视觉模型"，录入照样走品类默认值，不阻塞）。
  想在手机上用识别，去 `/settings` 填一次即可 —— 那份配置在云上，重新发布**不带 data** 时不会被顶掉。
- 顺带省一大截：`tools/`（Windows 安装包）与 `data/*.bak-*`（旧备份，本机实测 334 个文件 / 22.6MB）
  在 Linux 沙箱里没有意义。
- ⚠️ `stage` 会在**项目旁边的 `closet-stage/`** 留一份清单（原来是写死 `E:/closet-stage`，
  别人拿到源码就没法跑；要换位置设 `CLOSET_STAGE`）。**发完必须 `restore`**。
  清单还在时再跑 `stage` 会被挡住 —— 那是"状态不明，不许再挪"的保险。
  ⚠️ 清单里那几样**是搬走、不是删**（含 `serve.out.txt` 这个服务日志）。

## 已知限制

0. **重新发布带不带 `data/`，结果完全不同**（2026-09-30 实测两轮）。
   `stage_deploy.py` 的默认是**不带** → 云上那份保留、手机上改的留得住。
   但**同一份数据在两边各自往前走**，不自动合并 —— 想合流用 `pull_cloud.py`。
   详见《发到云上》第 ③ 条与《一个人用，两份设备怎么不分家》。
1. **物理合法 ≠ 好看**。硬规则只能保证穿出门不会犯物理错误（同槽位、温度不搭、撞色）。
   16℃ 能跑出几千套「有效搭配」，里面有不少是「换一双鞋」级别的微调，也有物理成立但视觉别扭的组合。
   这部分要靠大模型做审美过滤 —— 那正是接了模型之后「今日」多出来的那一步。
2. **图片做了裁边和 4:5 归一化，但没做抠图**。`rembg` 依赖较重（PyTorch），
   现在的做法是「找出照片背景色那一坨的外接框」把截图边框切掉（`app/imgs.py`）。
3. **「衣橱效率」的尺度已经改过一次**。原来是"合法路径数 ÷ 件数"，
   层级可变之后按乘法膨胀（28 件 20℃：320 → 2240 套）而失效；
   现在主指标换成**核心组合数**（512 个）与**组合密度**（100%）。
   密度要看它掉下来的时候 —— 那说明有衣服在互相打架，而不是衣服不够多。
4. **数据要自己盯**。`color_hex` 必须从校色后的图片取，不可能从商品图取 —— 否则取到的是当时的光，不是衣服的颜色。
5. ~~「内穿的裤子」无处安放~~ —— **已解决（2026-09-21）**：加了 `L4I` 槽位，
   秋裤按「内穿下装」录，只在 14℃ 以下出现，且被外裤盖住（不参与核心/撞色/正式度）。
   见上文「内穿下装（L4I）」。
6. **31℃ 以上整天排不出来**（2026-09-21 实测）。库里 7 件 T 恤全是 15~30℃、
   长裤 15~30 / 10~28、鞋 5~30 → 31℃ 时 L1/L4/L5 **三层合格数都是 0**。
   `diagnose` 会把这件事说清楚。**不是引擎 bug**：库里确实没有能穿到 31℃ 的东西。
   解药是录一条短裤（`L4` 下已有「短裤」品类，20~38℃）或凉鞋，别去调引擎的温度口径。
7. **洗几件就可能排不出来**（2026-09-23 实测）。26 件里洗掉 13 件，20℃ 一套都排不出来 ——
   按槽位排序取前 13 件，正好把内搭全洗了。**这是实话，不是 bug**：衣橱真的没得穿了。
   空态会说清"其中 N 件正在洗涤中，放回来可能就有解了"，并把恢复入口留在眼前。
   反过来说，这也正是这个产品的用法：它逼你看清"到底是衣服不够，还是今天没衣服"。
